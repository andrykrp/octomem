# Методика испытаний и ожидаемые результаты

Версия 2, 17.09.2026. Уточняет методы после независимого ревью Astra, не меняет
контракт протокола, лимиты продукта или обязательные пороги приёмки.

## 1. Три разных результата

1. **Исправность проверяющей системы:** негативные fixtures обязаны обнаруживать
   испорченные ответы, пропущенные поля, тайм-аут, ошибку клиента и неполный прогон.
2. **Результат испытания продукта:** конкретный контракт проверен на конкретной
   сборке. Зелёный тест драйвера сам по себе не доказывает исправность сервера.
3. **Готовность выпуска:** все обязательные наборы TEST-01…09 имеют доказательства
   на согласованном кандидате. Сумма успешных локальных прогонов этого не заменяет.

Коды процесса, JSON-вердикт и полнота отчёта проверяются совместно. Нулевой код
клиента не доказывает правильность каждого ответа. Отказ валидатора данных —
`INCONCLUSIVE` испытания, а не успешный или неуспешный результат продукта.

## 2. Оракулы протокола

- Проверять фактические байты, длины, значения, порядок, число ответов и EOF.
- `stats items/slabs` проверяются после создания заранее определённого непустого
  набора классов. Отсутствие ожидаемых классов не превращает проверку в PASS.
- Поля имеют точные имена и допустимые типы. Пропуск, дубликат или неполный ответ
  запрещён. Для детерминированных счётчиков задаются ожидаемые дельты действий.
- Known difference — конкретная разрешённая пара ответов/правило нормализации,
  а не разрешение игнорировать любые различия шага. Даже одинаковый неверный ответ
  двух серверов не считается соответствием контракту.
- Тайм-аут не равен EOF. Для `quit` нужен подтверждённый EOF; для `noreply` отдельно
  задаётся ограниченное окно тишины и последующий барьер ответа по тому же соединению.
- У каждого чтения абсолютный монотонный deadline и ограничение размера. Неудача
  потока клиента должна завершать команду неуспехом, а не уменьшать число работников
  незаметно для отчёта. Очистка дочерних процессов проверяется отдельно.

## 3. Конкуренция и отказы

Детерминированным называется только испытание с управляемым порядком нужных событий.
Барьер перед стартом большого числа операций не гарантирует проигрыш конкретного CAS.
Контенционный стресс публикует параметры, фактический охват и границы наблюдения;
серия зелёных повторов не доказывает отсутствие всех гонок.

`ActiveProcessorCount` — параметр JVM, не физическая CPU-affinity. Фиксировать оба,
если интерпретация результата зависит от параллельного исполнения.

Проверка освобождения pin должна измерять native/service charge до закрытия аллокатора:
успешное удаление ключа разрешено и при удерживаемой старой версии. Проверка callback
вне lock обращается к той же категории/блокировке и проверяет результат вне callback,
поскольку проверяемый код может намеренно проглатывать исключения callback.

Потенциальный deadlock изолируется дочерним JVM с жёстким deadline родителя. Одно
`@Timeout` и interrupt не гарантируют выход из неотменяемого monitor/lock ожидания.
Данные покрытия дочерних JVM собираются в отдельные файлы и объединяются штатным
JaCoCo до отчёта и проверки порогов; старые файлы после clean не используются.

## 4. Нагрузка: валидность раньше численного вердикта

Пороговые значения неизменны: M1 ≥ 0,90; M2 ≤ 1,25; M3 полный RSS ≤ 1,20 эталона.
Каждый обязательный сценарий оценивается отдельно, не по среднему разных сценариев.

До вычисления отношения проверяются идентичность JAR/эталона/JDK/драйвера,
полнота заранее объявленного числа пар, уникальность попыток, код выхода клиента,
успешность загрузки, параметры и фактический состав нагрузки, ответы, окно измерения
и достаточность нужных метрик. Неполные/ошибочные пары не удаляются молча. Старый
JSON от предыдущего запуска не может служить результатом новой попытки.

Сравнивать одинаковое определение нагрузки, а не требовать одинакового числа
завершённых операций за фиксированное время: последнее уничтожило бы смысл M1.
Фиксировать реальные доли операций, hit/miss, successful/error и переданные байты.
При вытеснении отдельно указывать разные фактические размеры резидентного набора.

Клиентский CPU ≥85% — сигнал для исследования, не доказательство bottleneck.
Атрибуция требует CPU обеих сторон, cgroup/throttling, временных рядов и вмешательства,
которое меняет доступную мощность клиента, сохраняя сценарий. Вывод П-08 нельзя
переносить на П-03. Неустановленная причина не отменяет наблюдаемые неблагоприятные
числа, но запрещает выдавать её за доказанную.

## 5. Память и устойчивое окно

Полный RSS, heap used/committed, native reserved/live/retired и логические платы
публикуются отдельно. Нативный счётчик не заменяет M3 по RSS. Разность cold/loaded RSS
содержит JIT, загрузку классов, heap commitment и временные объекты; это не точный
retained размер записи и не оценка асимптоты по трём небольшим наборам.

Параметры прогрева и критерий устойчивости фиксируются до запуска. Сохранять
timestamp каждой выборки; десять подряд мгновенных чтений — не десять независимых
наблюдений. Разделять startup, измерение и teardown. Если предобъявленное устойчивое
окно не достигнуто за ограниченное время, соответствующая метрика `INCONCLUSIVE`.
Диагностические JFR/NMT-прогоны отделяются от приёмочных; принудительный GC внутри
таймируемой нагрузки и подмена им RSS запрещены.

## 6. Повторения и статистика

По умолчанию планируются шесть пар в сбалансированном чередующемся порядке; число
пар, seed и правило остановки объявляются заранее. Для медианы применяется точный
непараметрический интервал по биномиальным рангам с указанными предпосылками.
При шести независимых непрерывных наблюдениях интервал min/max покрывает медиану
с вероятностью 96,875%; он может оставаться широким. Зависимость и дрейф стенда
требуют оговорок, а не фиктивного повышения точности.

Три прежние пары остаются исследовательским наблюдением. Их bootstrap min/max
нельзя обозначать надёжным 95% интервалом: при указанных предпосылках покрытие 75%.
Повторная выборка одних чисел не создаёт новых независимых наблюдений.

## 7. Планируемые результаты и история

| Проверка системы тестирования | Ожидаемый результат |
|---|---|
| Пустой/неполный `stats` при ожидаемых классах | Негативный результат с конкретным отсутствующим классом/полем |
| Испорченный known-difference ответ | Ошибка оракула продукта, не игнорирование по имени шага |
| Тайм-аут без FIN | Ошибка/незавершённость, не успешный EOF |
| Неверный код клиента, preload, хеш, пропущенная пара | INCONCLUSIVE с машинно-читаемой причиной до M1–M3 |
| Валидный набор, нарушающий неизменный порог | FAIL, без изменения ожиданий под результат |
| Валидный набор с достаточной точностью в пределах порога | PASS только соответствующей метрики/сценария |
| Не достигнуто устойчивое окно/не хватает измерений | INCONCLUSIVE, с сохранёнными сырыми данными |
| Совпадение/несовпадение закреплённого JAR | Явная проверка равенства; несовпадение блокирует успех команды |

Новые прогоны пишутся в уникальный каталог, после завершения не переписываются.
Хешировать исходники, тесты/ресурсы, POM, harness и артефакт; корректировка тестов
требует новых тестовых доказательств даже при прежнем JAR. Исторические отчёты,
созданные дефектным драйвером, сохраняются с отметкой о необходимых повторных
проверках. Изменение методики не даёт права задним числом объявить продукт PASS.

Два отдельных стенда запланированы владельцем. Вторая машина пока не проверена;
доверенный статус ОС и законный доступ требуют собственных доказательств. 72-часовой
прогон в текущую работу не входит и остаётся NOT_RUN, а не отменённым критерием релиза.
