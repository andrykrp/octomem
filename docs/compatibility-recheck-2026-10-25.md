## Итог инженерной работы 25.10.2026

После первичной сверки и дополнительного поручения владельца исправлены шесть production-файлов: `DefaultCacheEngine`, `CacheEngine`, `StorageAdmission`, `TextProtocolDecoder`, `CacheCommandDispatcher`, `TextConnectionHandler`. Код Memcached не включался в реализацию.

## Вывод

Цель владельца — самостоятельная реализация, на которую приложения переходят с Memcached преимущественно сменой адреса. Текущий контракт 1.0 существенно уже: классический текстовый протокол без binary, meta и аутентификации. Более того, обнаружены противоречия между отдельными требованиями Octomem и поведением выбранного эталона 1.6.45. Прохождение тестов, написанных только по этим требованиям, само по себе не доказывает совместимость.

**Универсальная замена Memcached не подтверждена.** Ниже разделены документально подтверждённые расхождения, исторические измерения и проверки, которые ещё нужно выполнить на текущем коде. Исходники приложения и тестов Octomem в этой сессии не анализировались; новые сборки и серверные прогоны не выполнялись.

Публичные материалы прочитаны 25.10.2026: [protocol.txt](https://github.com/memcached/memcached/blob/1.6.45/doc/protocol.txt), [proto_parser.c](https://github.com/memcached/memcached/blob/1.6.45/proto_parser.c), [proto_text.c](https://github.com/memcached/memcached/blob/1.6.45/proto_text.c), [items.c](https://github.com/memcached/memcached/blob/1.6.45/items.c), [thread.c](https://github.com/memcached/memcached/blob/1.6.45/thread.c). Это статическая сверка исходного эталона; запущенный эталон в этой сессии отсутствует.

## Найденные расхождения

### F1 — HIGH: область 1.0 не покрывает цель простой миграции любых клиентов

**Подтверждено по контракту**, а не новым сетевым тестом. README §6, docs/04 §1/§9/§11 и `compatibility-manifest.json:191–216` исключают binary, meta, UDP и SASL. TEST-02:32 прямо не заявляет универсальную замену клиентских экосистем.

Клиент, отправляющий binary или `mg`/`ms`, не становится совместимым только от смены адреса. Отказ от аутентификации при миграции недопустимо выдавать за совместимость. Эталон поддерживает также текстовую аутентификацию `-Y` (раздел Authentication в protocol.txt); ограничение не сводится к SASL.

Направление: после снятия исполнительных блокеров согласованно расширить требования и задачи совместимости. Очередь: точная семантика classic text → binary для существующих клиентов → meta (`mg/ms/md/ma/mn/me` и флаги) → режимы защиты и эксплуатационная совместимость. Это не выполненная реализация. UDP не включать автоматически: отдельный транспорт и дополнительная поверхность атак. TLS и Unix sockets включить в инвентаризацию режимов клиентов, не объявляя их поддержку без проверки.

### F2 — HIGH: внутреннюю версию записи нельзя автоматически отождествлять с wire-CAS

**Подтверждено противоречие требований эталону; поведение текущего Octomem NOT_RUN.** ЧТЗ-05-R02 требует смены версии при любом изменении; ADR-013:37 связывает это с `touch`/`gat`. В эталоне `process_touch_cmd` → `item_touch` → `do_item_touch` меняет срок, но не CAS. `do_item_touch` вызывает чтение с обновлением LRU и присваивает `exptime`; нового CAS на этом пути нет.

Регрессионный сценарий: `set k 0 0 1` со значением `x` → `gets k` (токен C) → `touch k 120` → `gets k` → `cas k 0 0 1 C` со значением `y`. При отсутствии конкурентных изменений и истечения срока эталон сохраняет C после touch и принимает cas. Если Octomem меняет C, приложение получает лишний `EXISTS`.

Направление: различать внутреннюю неизменяемую версию и видимый клиенту CAS; сохранение CAS при TTL-only обновлении не требует отказаться от безопасных снимков. Отдельно проверить `gat`/`gats`, промах, отрицательный TTL и конкурентное изменение данных. Текущий Java-код не проверен, поэтому дефект реализации не объявляется воспроизведённым.

### F3 — HIGH: сохранение старого значения при неуспешном SET расходится с эталоном

**Подтверждено противоречие контракта эталону; поведение текущего Octomem NOT_RUN.** ADR-013:12/17 включает `set` в общий принцип allocate/publish/retire и требует сохранять старую запись при отказе выделения. В `proto_parser.c::process_update_cmd_start` эталон при отказе `item_alloc` для `NREAD_SET` удаляет прежнее значение ключа — и при превышении размера, и при нехватке памяти. Для остальных команд этот блок не применяется.

Регрессионный сценарий: успешный `set k ...` → слишком большой `set k ...` с полностью переданным телом → `get k`. У эталона отказ записи не оставляет прежнее значение доступным. Дополнительно проверить OOM при запрещённом вытеснении и те же сценарии с `noreply`; после подавленного ответа поток должен остаться синхронизирован.

Влияние: приложение может продолжать получать устаревшие данные, хотя на Memcached ключ исчезал бы. Направление: отдельная семантика неуспешного SET в требованиях, затем независимый дифференциальный тест и минимальная правка. Не переносить удаление на `add`/`replace`/`cas` без проверки.

### F4 — MEDIUM: единая строка OOM и общий текст ошибки формата не совпадают со всеми командами эталона

**Подтверждено по требованиям и исходнику эталона.** docs/04:99 утверждает, что сокращённая `out of memory` в протоколе не используется, а таблица §7 задаёт единый ответ нехватки памяти. В `proto_parser.c::process_arithmetic_cmd`, ветка `EOM`, эталон возвращает `SERVER_ERROR out of memory`. Для записи используется `SERVER_ERROR out of memory storing object`.

Есть также специальные `CLIENT_ERROR invalid numeric delta argument` для неправильного delta и `CLIENT_ERROR invalid exptime argument` для ряда TTL-команд. Универсальная подстановка `bad command line format` не обеспечивает побайтового совпадения.

Направление: таблица ошибок по командам и причинам, включая `noreply`, а не одна общая строка. Ошибки формата, OOM счётчиков и OOM записи проверять раздельно. Фактические ответы текущего Octomem ещё не измерены.

### F5 — MEDIUM: максимальный размер записи уже измерялся как отличающийся

**Историческое измерение, не новый прогон.** Манифест:109–160 содержит ограниченную калибровку кандидата `950A8EDB…682B` против 1.6.45. Для ключа длиной 1 байт эталон принимал максимум 1 048 516 байт значения при flags=0 и 1 048 512 при flags≠0; Octomem — 1 048 543 независимо от flags. Различаются и границы ключей 16/250 байт.

Octomem в этой калибровке принимает больше, а не меньше: это не доказательство отказа миграции валидного значения с Memcached, но точное поведение на границе и обратимость переключения не совпадают. Манифест честно помечает результат `bounded=true`, `releaseAcceptance=false`; это не закрытый тест совместимости.

Направление: отдельная внешняя граница совместимости и отдельный внутренний бюджет Java-записи. Не зашивать структуру C или константу с одного ABI как универсальное правило; зафиксировать профиль эталона и проверить key/flags/CAS/config-варианты.

### F6 — MEDIUM: дедупликация и ограничение multi-get меняют наблюдаемое поведение

**Подтверждено различие контрактов.** docs/04:71 требует выдавать каждый ключ один раз. `proto_text.c::process_get_command` эталона последовательно обрабатывает каждую позицию, без такой дедупликации. При `get k k` для существующего ключа повторяется запись, тогда как контракт Octomem требует одну. Для счётчиков статистики повторные позиции также требуют сверки.

docs/04:19 ограничивает строку 8192 байт по умолчанию. Эталон в `try_read_command_ascii` имеет специальный путь расширения буфера для длинных `get`/`gets`. Следовательно, действующая клиентская пакетная выборка может не пройти после одной лишь смены адреса. Нельзя устранять защитные лимиты без безопасного ограниченного дизайна; нужны тесты длинных списков, дубликатов, пропусков и больших ответов.

### F7 — LOW: перечень известных отличий нуждается в перепроверке

**Подтверждена неточная классификация одиночного LF.** docs/04 §9 и манифест называют его известным отличием. Но `proto_parser.c::process_request` версии 1.6.45 явно принимает LF в строке команды ради обратной совместимости. Тело storage-команды по-прежнему требует CRLF. Это не повод расширять допуск для тела.

Legacy delete также нельзя объявлять отличием только по отсутствию аргумента в protocol.txt: комментарий и фактическая проверка аргументов в новом parser различаются по смыслу. Нужен прямой тест `delete k 0`, `delete k 1`, `delete k 0 noreply` против зафиксированного бинарного эталона. Пока это пункт проверки, не доказанное совпадение или новое расхождение.

## Исполнительный блокер и безопасный следующий шаг

**Исторический снимок первичной проверки:** следующие абзацы описывают предварительный блокер до восстановления заявлений владельца. Текущий статус — блокер инженерной работы снят, см. уточнение в начале отчёта. Числовые ссылки F2–F4 относятся к исходному документальному состоянию до коррекции 0.4; опорные идентификаторы — ЧТЗ-05-R02, ADR-013 и именованные функции эталона.

[docs/development.md:9](development.md), [REG:60–68](ref-registry-research.md) и [SEC-04:14](../security/SEC-04-access-and-secrets.md) требуют проверить допустимость передачи исходников моделям и размещение разработки/сборки. В просмотренных текущих документах и решениях владельца нет подтверждения для этой сессии. Это **не утверждение, что инфраструктура находится за рубежом**, а отсутствие необходимого факта по собственной политике проекта.

Поэтому исходники Octomem не отправлялись на анализ, новые кодовые изменения и сборки не выполнялись. Публичный исходник эталона изучать разрешил владелец; безопасная документальная сверка продолжена. Старые факты запуска тестов не заменяют подтверждение контура. Вопросы и запросы разрешений пользователю не направлялись.

Для продолжения нужен существующий проверяемый документ/решение о допустимом контуре: размещение машины и сборки, условия обработки/хранения исходников у модельного сервиса, права на результаты. Юридические и инфраструктурные факты нельзя восстановить догадкой.

После снятия этого блокера порядок работы:

1. Зафиксировать исходный набор и отдельный диагностический кандидат, не перезаписывая frozen-доказательства.
2. Независимому автору тестов воспроизвести F2/F3/F4 и проверить F5/F6/F7 на двух отдельных серверах с точными версиями и настройками. CAS сравнивать как отношения токенов внутри сервера, а не как равенство чисел между процессами.
3. Уточнить требования и задачи до правок реализации. Не объявлять расхождение нормой только ради прохождения существующих тестов.
4. Исправить подтверждённые дефекты с сохранением владения памятью, ограниченных буферов, потокового кадрирования и безопасности; затем свежие unit/IT/coverage, дифференциальные тесты и независимое ревью.
