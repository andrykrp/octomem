# octomem: спецификация совместимости протокола

> **Расширение поручения 25.10.2026:** владелец потребовал реализовать отсутствующие binary/meta для максимально простой миграции. Старые исключения этих протоколов ниже описывают исходный1.0 baseline, не действующее ограничение работ. Обязательная область расширения — [T-019](../tasks/T-019-expanded-memcached-protocols.md), архитектура — [ADR-020](adr/ADR-020-memcached-protocol-families.md). До завершения реализации/испытаний это требование, а не заявление поддержки. Действующие classic-семантика, ограничения памяти и критерии тестирования не отменяются.

Версия 0.3 от 14.09.2026. Документ приоритетен для всех спорных случаев поведения. Правка 0.2: отображение `CacheCapacityException` (`touch`/`gat`/`gats`) в `SERVER_ERROR out of memory storing object`, неизменность старой записи и атомарность multi-gat по R-04 (открыт). Правка 0.3: `gat`/`gats` не поддерживают `noreply` и всегда отвечают, лексема `noreply` — обычный ключ; подавление отказа ёмкости только у `touch` при явной лексеме.

Нормативный ориентир: спецификация протокола Memcached <https://github.com/memcached/memcached/blob/1.6.45/doc/protocol.txt>. Где эта спецификация молчит, ориентиром служит поведение выбранной версии эталонного Memcached, зафиксированной в манифесте совместимости.

### Коррекция совместимости от 25.10.2026 (версия 0.4)

**Статус исполнения:** первоначальное NOT_RUN ниже — состояние до реализации. После исправлений 128 независимых регрессий прошли; полный verify и дополнительная сверка числовой грамматики продолжаются. Точная идентичность и дальнейший итог — [checkpoint](../.opencode/auto-omo-gpt/run_fb08f2b2d70d.md). Это не приёмка выпуска.

По поручению владельца о максимальной совместимости и немедленных правках уточнены требования ниже. Они имеют приоритет над прежними общими формулировками о смене CAS при любом изменении и сохранении значения при любом отказе SET. Основание — [повторная сверка](compatibility-recheck-2026-10-25.md), F2–F4, с исходным эталоном 1.6.45. Реализация и новые тесты **NOT_RUN**; исторические результаты не переносятся. Архитектурное разграничение — [ADR-019](adr/ADR-019-wire-cas-and-set-failure.md), задача — [T-018](../tasks/T-018-classic-compatibility-corrections.md).

- Успешное изменение только TTL через `touch`/`gat`/`gats` сохраняет видимый клиенту CAS. Новая внутренняя неизменяемая версия может иметь прежний wire-CAS. Изменение данных через storage-команды и счётчики по-прежнему обновляет CAS.
- При отказе выделения записи для синтаксически корректного `set` из-за превышения полного размера записи либо нехватки памяти прежнее значение этого ключа инвалидируется, как в `process_update_cmd_start` эталона. Нельзя распространять эту семантику на другие команды, ошибки синтаксиса или произвольный сбой JVM. Отдельно проверить отказы входного admission и поздней загрузки тела: эквивалентность фаз не установлена, их оракул не выводится из общего слова OOM.
- Старая уже захваченная версия может оставаться у читателя до освобождения удержаний. Инвалидация меняет доступность для новых чтений и не разрешает повреждать или преждевременно освобождать удержанную память.
- Ошибка OOM зависит от операции и фазы: начальное выделение входной storage-записи — `SERVER_ERROR out of memory storing object`; `incr`/`decr` при отказе арифметической операции — `SERVER_ERROR out of memory`. После успешного допуска входного фрагмента `append`/`prepend` отказ выделения объединённого значения или превышение его размера даёт `NOT_STORED`, старое значение сохраняется (`do_store_item` эталона). Для проектного отказа выделения при TTL-only обновлении и отказа допуска снимка сохраняется явно заданный ниже ответ; это дополнительный путь Octomem, а не доказанное совпадение доступности операции с эталоном.
- Неверная числовая дельта `incr`/`decr` — `CLIENT_ERROR invalid numeric delta argument`. Неверный `exptime` у `touch`/`gat`/`gats`/`flush_all` — `CLIENT_ERROR invalid exptime argument`. Ошибка flags/exptime в заголовке storage-команды остаётся `CLIENT_ERROR bad command line format`. Для сочетания нескольких ошибок порядок проверки уточняется дифференциальными тестами.
- Валидный `noreply` подавляет ответы и в перечисленных прикладных отказах, но не отменяет изменение состояния. `gat`/`gats` по-прежнему не имеют режима `noreply`; правила невосстановимого кадрирования сохраняются.
- LF в строке команды принимается и эталоном 1.6.45; это не отличие от него. Данные storage-команды по-прежнему завершаются CRLF.
- У `touch`/`gat`/`gats`/`flush_all` wire-exptime разбирается как знаковое 32-битное число (от −2147483648 до 2147483647); выход за диапазон даёт соответствующую ошибку команды. Storage-команды выбранного Linux LP64 эталона используют signed long с последующим сужением до int32: Octomem повторяет этот зафиксированный профиль, разбирая signed64 и применяя младшие 32 бита до семантики TTL. Например, 4294967296 превращается в 0, а 2147483648 — в отрицательное истечение. Это особенность проверенной сборки 1.6.45, не универсальная гарантия C ABI. Внутренний API/часы остаются long; сценарии long API и wire не смешиваются.
- Грамматика чисел зависит от команды эталона: `touch`/`gat`/`gats`/`flush_all` используют mcmc-разбор (не принимают начальный `+`, длина токена не более 11 байт); storage-exptime использует safe_strtol (начальный `+` допустим). Беззнаковые delta/CAS токены ограничены 22 байтами, даже если длинная строка ведущих нулей помещается по числовому значению. Пограничные лексемы проверяются отдельно по зафиксированному эталону; общая Java-функция signed не задаёт wire-контракт.
- Зафиксированная особенность 1.6.45: одиночный `-` у перечисленных mcmc TTL-команд означает 0, а storage-exptime его отвергает. Это подтверждено отдельным локальным дифференциальным прогоном 25.10.2026; не обобщать особенность на другие версии и другие числовые поля.

Остальные действующие гарантии, включая ограниченные снимки, дедупликацию, атомарность multi-gat, лимиты и независимое авторство тестов, не ослабляются. Binary/meta и режимы защиты требуют отдельного расширения профиля; настоящая коррекция не объявляет их реализованными.

## 1. Область

Текущая приёмка от 15.09.2026: координатор принял ADR-013/015 и [ADR-016](adr/ADR-016-bounded-command-snapshots.md) после ревью без замечаний `97c8c23b86be`. R-04/R-05/R-08/R-09 закрыты как DESIGN findings, R-07 уже закрыт; реализация интерфейсов T-004 разрешена. Это не PASS совместимости, тестов, производительности или релиза. Статусы правок 0.2/0.3 в заголовке и истории документа исторические, не текущие; атомарность, дедупликация и defaults сохранены.

Выпуск 1.0 поддерживает **текстовый протокол Memcached** без мета-команд. Бинарный протокол, мета-команды `mg`, `ms`, `md`, `ma`, а также нестандартные административные команды `watch`, `lru_crawler`, `cache_memlimit`, `shutdown` в 1.0 не поддерживаются и перечислены в разделе 9.

## 2. Кадрирование

- Команды разделяются `\r\n`. Одиночный `\n` допускается как завершение строки для устойчивости.
- Команда записи состоит из строки команды и блока данных ровно `<bytes>` байт, завершённого `\r\n`.
- Пустая строка между командами недопустима и даёт `ERROR`.
- Сервер разбирает поток: одна команда может быть разбита на несколько TCP-сегментов, несколько команд могут прийти в одном сегменте.
- Максимальная длина строки команды задаётся настройкой, по умолчанию 8192 байта. Превышение — `CLIENT_ERROR bad command line format` с последующим закрытием соединения при невозможности восстановить поток.
- Ключ: не более 250 байт, без пробелов и управляющих символов. Превышение или недопустимый символ — `CLIENT_ERROR bad command line format`.
- Размер хранимой записи ограничен настройкой `item.maxSize`, по умолчанию 1 МиБ. Предел применяется к **полной записи** (ключ, служебные поля и значение), как у эталонного Memcached. Поэтому максимальный размер самого значения немного меньше и зависит от длины ключа; точная граница фиксируется в манифесте совместимости и проверяется тестом.

## 3. Команды чтения

### 3.1. `get`

```text
get <key1> [<key2> ...]\r\n
```

Ответ для каждой найденной записи:

```text
VALUE <key> <flags> <bytes>\r\n
<data>\r\n
```

Завершение:

```text
END\r\n
```

Если ни одна запись не найдена, ответ содержит только `END\r\n`.

`get`/`gets`/`gat`/`gats` наблюдают все ключи и TTL на один `capturedClock` под всеми затронутыми блокировками; pin неизменяемых найденных версий получены до unlock. Промах остаётся промахом после конкурентной вставки, попадание не отзывается из-за истечения TTL во время выдачи. Ответ последовательно сериализует снимок, не перечитывая живые записи. Резерв метаданных снимка берётся целиком до захвата и первого байта; отказ допуска даёт только `SERVER_ERROR out of memory storing object\r\n`, без VALUE/END частичного ответа. После начала выдачи отсутствие буферного бюджета вызывает backpressure, не поздний отказ допуска (ADR-016).

### 3.2. `gets`

То же, но в строке `VALUE` добавляется уникальная версия:

```text
VALUE <key> <flags> <bytes> <cas>\r\n
```

**Формат версии.** Токен `cas` — беззнаковое 64-битное десятичное число. Его нужно разбирать и выводить как беззнаковое: значения выше `Long.MAX_VALUE` допустимы. Это важно при реализации на Java, где `long` знаковый.

### 3.3. `gat` и `gats`

```text
gat <exptime> <key1> [<key2> ...]\r\n
gats <exptime> <key1> [<key2> ...]\r\n
```

Чтение с одновременным обновлением срока жизни. `gats` дополнительно возвращает версию, как `gets`.

Обновление срока требует новой версии записи (ADR-013). Multi-`gat`/`gats` по ADR-016 под всеми затронутыми блокировками сначала готовит все новые версии, резервы и снимок результата, затем публикует весь набор. Отказ подготовки сигнализируется проверяемым `CacheCapacityException` и даёт `SERVER_ERROR out of memory storing object` до первого байта. Ни одно исходное значение, TTL или `cas` не меняется; все неопубликованные версии, резервы и удержания освобождаются. Каждый уникальный ключ обновляется один раз. `gat`/`gats` **не поддерживают** `noreply`: всегда отвечают, а эта лексема в позиции ключа считается обычным ключом. R-04 закрыт как DESIGN finding после принятия ADR-016; тесты реализации обязательны.

### 3.4. Повторяющиеся ключи

Поведение при повторяющемся ключе в одной команде не определено спецификацией. octomem возвращает каждую запись не более одного раза, в порядке первого появления ключа. Клиент не должен полагаться на повторный вывод. Это известное отличие сохраняется при ADR-016; снимок удерживает уникальную версию один раз, multi-gat обновляет уникальный ключ один раз.

## 4. Команды записи

### 4.1. Синтаксис

```text
set     <key> <flags> <exptime> <bytes> [noreply]\r\n<data>\r\n
add     <key> <flags> <exptime> <bytes> [noreply]\r\n<data>\r\n
replace <key> <flags> <exptime> <bytes> [noreply]\r\n<data>\r\n
append  <key> <flags> <exptime> <bytes> [noreply]\r\n<data>\r\n
prepend <key> <flags> <exptime> <bytes> [noreply]\r\n<data>\r\n
cas     <key> <flags> <exptime> <bytes> <cas unique> [noreply]\r\n<data>\r\n
```

`append` и `prepend` принимают `flags` и `exptime` в строке команды, но **не применяют** их: изменяются только данные, а флаги и срок жизни существующей записи сохраняются.

### 4.2. Ответы

| Команда | Успех | Отказ |
|---|---|---|
| `set` | `STORED` | `SERVER_ERROR out of memory storing object` |
| `add` | `STORED` | `NOT_STORED` |
| `replace` | `STORED` | `NOT_STORED` |
| `append` | `STORED` | `NOT_STORED` |
| `prepend` | `STORED` | `NOT_STORED` |
| `cas` | `STORED` | `EXISTS` при несовпадении версии, `NOT_FOUND` если ключа нет |

При начальном выделении входной storage-записи возможны `SERVER_ERROR object too large for cache` при превышении размера и `SERVER_ERROR out of memory storing object` при нехватке памяти после вытеснения. После допуска входного фрагмента отказ выделения/превышение размера объединённого значения `append`/`prepend` возвращает `NOT_STORED` без изменения прежней записи. Для `incr`/`decr` действует отдельная строка OOM из коррекции 25.10.2026.

### 4.3. Семантика `exptime`

| Значение | Поведение |
|---|---|
| `0` | Без срока жизни |
| От `1` до `2592000` (30 суток) | Относительный срок в секундах от текущего момента |
| Больше `2592000` | Абсолютный момент времени как Unix-время в секундах |
| Отрицательное | Запись считается уже просроченной |

Спецификация Memcached описывает отрицательное значение как немедленное истечение срока. octomem следует этому поведению и не относит его к известным отличиям.

### 4.4. `flags`

Флаги — 32-битное беззнаковое число, непрозрачное для сервера. Значение больше `2^32 − 1` даёт `CLIENT_ERROR bad command line format`. octomem возвращает флаги без изменений.

### 4.5. Превышение размера записи

Если запись не помещается в предел `item.maxSize` (с учётом ключа и служебных полей), сервер **обязан прочитать и отбросить** блок данных указанного в команде размера `<bytes>`, чтобы не нарушить поток, и затем ответить `SERVER_ERROR object too large for cache`. Молчаливое закрытие соединения запрещено, кроме случая, когда восстановить поток невозможно.

### 4.6. `noreply`

Суффикс `noreply` подавляет **любой** ответ команды: успех (`STORED`, `DELETED`, `TOUCHED`, `OK`, новое значение счётчика), прикладные отказы (`NOT_STORED`, `EXISTS`, `NOT_FOUND`) и серверные ошибки (`object too large for cache`, `out of memory storing object`). Клиент, использующий `noreply`, сознательно не узнаёт результат.

Единственное исключение — нарушение кадрирования, из-за которого поток команд невозможно восстановить: неверная строка команды или неверный блок данных. Тогда сервер отправляет `CLIENT_ERROR` либо закрывает соединение, чтобы не разбирать последующие команды неверно. Это поведение проверяется в Т-01.

## 5. Команды изменения и удаления

### 5.1. `delete`

```text
delete <key> [<time>] [noreply]\r\n
```

Ответ: `DELETED` или `NOT_FOUND`.

Современный синтаксис — `delete <key> [noreply]`. Устаревший необязательный аргумент `<time>` octomem принимает и игнорирует как расширение совместимости со старыми клиентами. Выбранный эталон может отвергать этот аргумент, поэтому поведение фиксируется в перечне известных отличий и учитывается в дифференциальном тесте.

### 5.2. `incr` и `decr`

```text
incr <key> <value> [noreply]\r\n
decr <key> <value> [noreply]\r\n
```

Ответы:

- Новое значение в десятичном виде.
- `NOT_FOUND`, если ключа нет.
- `CLIENT_ERROR cannot increment or decrement non-numeric value`, если хранимое значение не является десятичным числом.

Числа — беззнаковые 64-битные. `incr` при переполнении заворачивается по модулю `2^64`. `decr` при вычитании больше текущего значения даёт `0` и **не** заворачивается — как у эталонного Memcached. Операция изменяет версию записи.

### 5.3. `touch`

```text
touch <key> <exptime> [noreply]\r\n
```

Ответ: `TOUCHED` или `NOT_FOUND`. Семантика `exptime` совпадает с разделом 4.3.

Восстановимый отказ выделения при обновлении срока сигнализируется проверяемым `CacheCapacityException`, а не ответом `NOT_FOUND` и не значением `false`: движок отображает его в `SERVER_ERROR out of memory storing object`. Старая запись, её срок и `cas` не меняются; удержания освобождаются. При **явной** лексеме `noreply` у `touch` ответ подавляется; это относится только к `touch` — `gat`/`gats` всегда отвечают, а `noreply` в них является обычным ключом (раздел 3.3).

### 5.4. `flush_all`

```text
flush_all [<delay>] [noreply]\r\n
```

Ответ: `OK`. Без аргумента инвалидирует все записи немедленно. Аргумент `<delay>` преобразуется так же, как `exptime`: значение не больше 2 592 000 — относительное число секунд, больше — абсолютный момент Unix-времени. Поэтому большие значения означают конкретное время, а не «через много дней». Механизм: запоминается момент `oldest_live`; записи, созданные не позже этого момента, считаются просроченными. Записи, созданные после, сохраняются.

## 6. Служебные команды

### 6.1. `stats`

```text
stats\r\n
stats items\r\n
stats slabs\r\n
stats reset\r\n
```

Ответ — строки `STAT <name> <value>\r\n`, завершение `END\r\n`. `stats reset` отвечает `RESET\r\n`.

Обязательные поля общего `stats`:

| Группа | Поля |
|---|---|
| Процесс | `pid`, `uptime`, `time`, `version`, `pointer_size`, `threads` |
| Соединения | `curr_connections`, `total_connections`, `connection_structures`, `conn_yields` |
| Команды | `cmd_get`, `cmd_set`, `cmd_flush`, `cmd_touch` |
| Попадания | `get_hits`, `get_misses`, `delete_hits`, `delete_misses`, `incr_hits`, `incr_misses`, `decr_hits`, `decr_misses`, `cas_hits`, `cas_misses`, `cas_badval`, `touch_hits`, `touch_misses` |
| Данные | `curr_items`, `total_items`, `bytes`, `reclaimed`, `expired_unfetched`, `evicted_unfetched` |
| Память | `limit_maxbytes`, `evictions` |
| Ввод-вывод | `bytes_read`, `bytes_written` |

`eviction_policy` встречается в общем `stats` части версий Memcached. Для обязательного профиля он не требуется; если эталон его выводит, octomem повторяет поле для совместимости. Это фиксируется в манифесте.

Обязательные поля `stats items` (для каждого класса `N`): `items:N:number`, `items:N:age`, `items:N:evicted`, `items:N:evicted_nonzero`, `items:N:evicted_time`, `items:N:outofmemory`, `items:N:tailrepairs`, `items:N:reclaimed`, `items:N:expired_unfetched`, `items:N:evicted_unfetched`, `items:N:crawler_reclaimed`.

Обязательные поля `stats slabs` (для каждого класса `N`): `N:chunk_size`, `N:chunks_per_page`, `N:total_pages`, `N:total_chunks`, `N:used_chunks`, `N:free_chunks`, `N:free_chunks_end`, `N:get_hits`, `N:cmd_set`, `N:delete_hits`, `N:incr_hits`, `N:decr_hits`, `N:cas_hits`, `N:cas_badval`, `N:mem_requested`.

Точные имена и состав полей зависят от выбранной версии эталона. Итоговый перечень фиксируется в манифесте совместимости до реализации и проверяется в Т-01.

Расширенные поля (`stats sizes`, `stats conns`, `stats cachedump`) относятся к P2 и в 1.0 не поддерживаются.

### 6.2. `version`

```text
version\r\n -> VERSION <строка>\r\n
```

Строка версии документируется и **не должна выдавать octomem за оригинальный Memcached**. Рекомендуемый вид: `VERSION 1.0.0 (octomem)`.

### 6.3. `verbosity`

```text
verbosity <level> [noreply]\r\n -> OK\r\n
```

### 6.4. `quit`

```text
quit\r\n
```

Ответ не отправляется, соединение закрывается.

## 7. Ошибки

| Условие | Ответ |
|---|---|
| Неизвестная команда | `ERROR\r\n` |
| Неверный формат команды, ключ или флаги (кроме специальных числовых ошибок ниже) | `CLIENT_ERROR bad command line format\r\n` |
| Неверная дельта `incr`/`decr` | `CLIENT_ERROR invalid numeric delta argument\r\n` |
| Неверный exptime у `touch`/`gat`/`gats`/`flush_all` | `CLIENT_ERROR invalid exptime argument\r\n` |
| Неверный блок данных | `CLIENT_ERROR bad data chunk\r\n` |
| Начальная входная storage-запись слишком велика | `SERVER_ERROR object too large for cache\r\n` |
| Нет памяти при начальном выделении storage-записи или проектном допуске снимка/TTL-версии | `SERVER_ERROR out of memory storing object\r\n` |
| Отказ выделения/превышение размера объединённого append/prepend после допуска фрагмента | `NOT_STORED\r\n` |
| Нет памяти для `incr`/`decr` | `SERVER_ERROR out of memory\r\n` |
| Нечисловое значение в `incr`/`decr` | `CLIENT_ERROR cannot increment or decrement non-numeric value\r\n` |
| Внутренняя ошибка | `SERVER_ERROR <текст>\r\n` |

`CLIENT_ERROR` и `SERVER_ERROR` сопровождаются текстом на английском языке, как у эталона. Русский язык интерфейса относится к документации и не меняет строки протокола.

Строка `SERVER_ERROR out of memory storing object` покрывает также проектный восстановимый отказ `CacheCapacityException` при `touch` и `gat`/`gats`. Её нельзя заменять сокращённой строкой на этом пути. Наличие отказа TTL-операции из-за копирования записи — отдельное отличие доступности от эталона; оно должно измеряться, а не исчезать за совпадением текста storage-ошибки.

## 8. Конвейер и параллелизм

- Команды одного соединения выполняются по порядку.
- `noreply` не освобождает от соблюдения порядка.
- Разные соединения обрабатываются параллельно; одиночная команда атомарна.
- Обновление срока в multi-`gat`/`gats` атомарно по всем ключам: prepare-all-before-publish и полный откат при отказе по принятому ADR-016; R-04 закрыт как DESIGN finding, FR-40 не сужен до ключа.
- Ответ передаётся потоково и не обязан быть подготовлен целиком до начала отправки.
- Сервер сохраняет локальные inflight/pending лимиты. Body admission по ADR-016 резервирует объявленный payload+32 целиком до allocation/bodyread; при отказе немедленно выбирает OOM, отбрасывает ровно тело и CRLF собственной receive/discard lane и только затем выдаёт ошибку/продолжает pipeline. Правильный noreply подавляет ошибку; malformed terminator закрывает невосстановимый поток, тело не разбирается как команды. Каждое соединение имеет независимую transmit lane для всех ответов/ошибок; отсутствие общего burst pool не препятствует прогрессу здорового клиента и CRLF2 даже при крошечном memory.limit. Переполнение собственной lane приостанавливает только это соединение; round-robin без spin и unlimited очередей не меняет порядок ответов.

## 9. Известные отличия от эталона

Line slot допускается до чтения: charge `2L * L + 256`, perconn `satMul(maxInflight,charge)`, global `satMul(connections.max,perconn)`. Только LIMIT насыщаются до Long.MAX_VALUE, не отвергая config и не урезая wire/public limits; CAS reserve использует `charge <= limit-used` без насыщения реальных счётчиков. Full pipeline отключает OP_READ без body reserve ради slot, control продолжает ответы. Engine.KeySequence передаёт borrowed immutable raw backing/offset/length последовательным visitor до command release; нет per-token arrays/views/List, N считается одним scan. Snapshot резервируется перед allocation и заполняется линейным pass при двойном учёте пика; дедупликация первого появления и max key250 неизменны (ADR-016 M1/M2).

| Отличие | Причина | Статус |
|---|---|---|
| Нет бинарного протокола | Ограничение выпуска 1.0 | P3 |
| Нет мета-команд | Ограничение выпуска 1.0 | P2 |
| Нет `stats sizes`, `stats conns`, `stats cachedump` | Редкое использование, стоимость учёта | P2 |
| Нет UDP | Упрощение и безопасность | P2 по запросу |
| Нет SASL | Соответствие по умолчанию, безопасность сетевая | P2 |
| Нет нестандартных `watch`, `lru_crawler`, `cache_memlimit`, `shutdown` | Административные команды вне протокола | Не планируются |
| Повторяющиеся ключи в `get` выводятся один раз | Определено в 3.4 | Известное отличие |
| Устаревший аргумент `<time>` у `delete` принимается и игнорируется | Совместимость со старыми клиентами | Известное отличие |
| Одиночный `\n` принимается как завершение строки | Устойчивость к нестандартным клиентам | Совпадает с 1.6.45; ранее ошибочно классифицировано как отличие |
| Ограничение длины строки команды (по умолчанию 8192 байта) | Защита от перегрузки | Известное отличие; настраивается |
| Строка `version` содержит признак `octomem` | Честность происхождения | Известное отличие |

Этот перечень — часть контракта. Новое отличие добавляется сюда до выпуска и сопровождается тестом.

## 10. Манифест совместимости

До начала реализации фиксируется файл `compatibility-manifest.json`:

```json
{
  "octomemVersion": "to-be-assigned",
  "referenceMemcachedVersion": "to-be-selected",
  "referenceSourceSha256": "to-be-recorded",
  "protocol": "text",
  "commands": [],
  "statsFields": [],
  "platforms": [],
  "knownDifferences": []
}
```

Пустые списки в примере означают «подлежит заполнению», а не «ничего не требуется». Версия эталона не может быть `latest`.

## 11. Миграция приложения

1. Зафиксировать используемый клиент, его версию, режим (текст/бинарный) и набор команд.
2. Убедиться, что клиент работает по текстовому протоколу и не требует мета-команд или SASL.
   Отдельно проверить текстовую аутентификацию Memcached `-Y`, TLS и Unix sockets: отсутствие SASL не означает отсутствие требований защиты/транспорта. Отключение защиты или смена транспорта не засчитывается как «только смена адреса»; неподдержанный обязательный режим блокирует такой пилот.
3. Заменить адрес и порт Memcached на адрес и порт octomem.
4. Не менять ключи, флаги, формат значений и границы транзакций приложения.
5. Выполнить прикладные тесты и нагрузочный прогон на octomem.
6. Сверить `stats`: попадания, промахи, вытеснения, память.
7. Зафиксировать результат как протокол пилотной миграции.

Если для перехода требуется изменить код приложения, пилот не считается успешным для цели M5.
