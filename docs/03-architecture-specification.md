# octomem: задание на архитектуру

> **Коррекция совместимости 25.10.2026:** [docs/04, версия 0.4](04-protocol-compatibility-specification.md) и [ADR-019](adr/ADR-019-wire-cas-and-set-failure.md) уточняют внешнюю семантику без отказа от неизменяемых версий. Wire-CAS сохраняется при TTL-only обновлении, но не служит идентичностью физического блока. Начальный отказ выделения SET инвалидирует индекс по ключу; удержанные версии живут до закрытия leases. Общие формулировки ниже «OOM сохраняет старое» не применяются к этому узкому случаю. Дедупликация, полная атомарность снимков, бюджеты, lock order и конфигурационные defaults сохранены. Реализация и проверка отслеживаются в T-018, не считаются принятыми по одной правке документа.

Версия 0.7 от 15.09.2026. ADR-013/015/016 ACCEPTED координатором после независимого ревью без замечаний `97c8c23b86be`; R-04/R-05/R-08/R-09 закрыты как DESIGN findings. ADR-014 и закрытый R-07 сохраняют точный граф §3. Разрешена реализация интерфейсов T-004 по принятому контракту; завершение/заморозка задачи требуют её приёмки, PASS реализации/тестов/производительности/релиза не заявлен. Разрешение владельца заменяет только однозаписное и независимое от ответа удержание; FR-40, wire-дедупликация, `noreply` и четырнадцать defaults сохранены.

## 1. Архитектурные драйверы

- Совместимость протокола важнее собственных удобств: внешнее поведение определяется спецификацией 04.
- Предсказуемая память: значения хранятся вне объектов Java, потребление ограничено настройкой.
- Минимум зависимостей: ядро работает на одной JDK без сторонних runtime-библиотек.
- Простые границы модулей: транспорт, протокол, движок, хранилище, служебные подсистемы.
- Один процесс, один узел, отсутствие внешних сервисов.

## 2. Контекст и контейнер

```text
Клиент Memcached
      |  TCP, текстовый протокол
      v
+-----------------------------------------------------------+
|                       процесс octomem                      |
|                                                            |
|  +-------------+   +--------------+   +----------------+  |
|  |  transport  |-->|   protocol   |-->|     engine     |  |
|  |  (java.nio) |<--|    (text)    |<--|  (CacheEngine) |  |
|  +-------------+   +--------------+   +-------+--------+  |
|                                             |              |
|                    +------------------------+-----------+  |
|                    |            storage                 |  |
|                    |  hash table | slab allocator | LRU |  |
|                    +------------------------------------+  |
|                                                            |
|  +----------+ +----------+ +----------+ +----------------+ |
|  |  expiry  | |  stats   | |  config  | |     logging    | |
|  +----------+ +----------+ +----------+ +----------------+ |
+-----------------------------------------------------------+
```

Движок не знает о сети, транспорт не знает о хранении, протокол знает только команды и ответы. Это позволяет менять транспорт, добавлять мета-команды и тестировать подсистемы отдельно.

| `ru.octomem.util` | Часы, хеширование, утилиты | — |

**Правило зависимостей.** Разрешённый набор зависимостей задан в столбце «Зависит от». Граф зависимостей ацикличен. `stats` и `util` не зависят ни от чего, кроме JDK. `util` разрешён только перечисленным потребителям (`engine`, `storage`, `expiry`, `transport`, `protocol`) и только для чистых утилит; `stats` не входит в число потребителей `util` и остаётся пакетом только на JDK (авторитетная таблица рёбер). Обратные рёбра и циклы запрещены. Рёбра `config`, `cli` и `eviction` сохраняются как прежде. Нарушение проверяется сборкой и тестом архитектуры Т-02. Точный граф и владение типами зафиксированы в [ADR-014](adr/ADR-014-package-dependency-edges.md): `Item`/`ItemLease` принадлежат `storage`, `GetResult` и `CacheCapacityException` — `engine`, а прямое ребро `protocol → storage` разрешено для сегментного чтения значения.

## 4. Ключевые интерфейсы

Интерфейсы фиксируются до параллельной разработки. Изменение интерфейса оформляется ADR.

### 4.1. Движок

```java
package ru.octomem.engine;

public interface CacheEngine {
    // Один снимок целой команды; порядок первого появления, без дублей.
    RetrievalSnapshot snapshot(KeySequence keys) throws CacheCapacityException;
    RetrievalSnapshot snapshotAndTouch(KeySequence keys, long exptime)
        throws CacheCapacityException;
    GetResult get(byte[] key);                    // без версии
    GetResult getWithCas(byte[] key);             // с версией
    GetResult getAndTouch(byte[] key, long exptime) throws CacheCapacityException;

    StoreResult set(byte[] key, byte[] value, int flags, long exptime);
    StoreResult add(byte[] key, byte[] value, int flags, long exptime);
    StoreResult replace(byte[] key, byte[] value, int flags, long exptime);
    StoreResult append(byte[] key, byte[] value);
    StoreResult prepend(byte[] key, byte[] value);
    StoreResult cas(byte[] key, byte[] value, int flags, long exptime, long casId);

    boolean delete(byte[] key);
    CounterResult increment(byte[] key, long delta);
    CounterResult decrement(byte[] key, long delta);
    boolean touch(byte[] key, long exptime) throws CacheCapacityException;
    void flushAll(long delaySeconds);

    void start();
    void stop();
}
```

```java
public class CacheCapacityException extends Exception {   // checked
    // Только ограниченные метаданные (например, требуемый размер блока и предел).
    // Свободные тексты внутренних ошибок не переносятся.
}
```

`CacheCapacityException` принадлежит `ru.octomem.engine` и сообщает о восстановимом отказе выделения новой версии при `touch`/`getAndTouch` либо допуска/подготовки `snapshot`/`snapshotAndTouch`. Отказ не кодируется `false` или промахом. Протокольный обработчик переводит исключение в `SERVER_ERROR out of memory storing object` до первого байта ответа чтения; при явном `noreply` подавление действует только для `touch`. `get`/`gets`/`gat`/`gats` всегда отвечают. При отказе все временные удержания и резервы освобождаются, ни один исходный ключ, TTL или `cas` не изменён. Метаданные исключения ограничены и не содержат внутренних сообщений. По ADR-016 команды чтения используют один вызов снимка, а не цикл одиночных методов `get*`; одиночные `GetResult` не заменяют командный снимок.

`StoreResult` принимает значения `STORED`, `NOT_STORED`, `EXISTS`, `NOT_FOUND`, `TOO_LARGE`, `OUT_OF_MEMORY`, `INVALID`. `GetResult` реализует `AutoCloseable` и удерживает найденную запись: он даёт доступ к `Item` и обязан быть закрыт после выдачи значения. `CounterResult` содержит новое значение или причину отказа.

### 4.2. Модель записи

Типы записи принадлежат хранилищу, тип результата чтения — движку ([ADR-014](adr/ADR-014-package-dependency-edges.md)): `Item` и `ItemLease` — `ru.octomem.storage`, `GetResult` — `ru.octomem.engine`.

```java
package ru.octomem.storage;

public interface Item {
    // Защитная копия ключа либо явно ограниченное представление только для чтения.
    // Изменяемые хранимые байты ключа не выдаются.
    byte[] key();
    int flags();
    long expiryTime();   // абсолютное время в секундах, 0 — без срока
    long casId();
    int valueLength();
    // Читает до dst.remaining() байт значения начиная со смещения offset.
    // Возвращает число прочитанных байт; 0 — конец значения.
    int readValue(long offset, ByteBuffer dst);
    boolean isExpired(long now);
    // Активность и удержание — отдельное изменяемое служебное состояние;
    // эти методы не меняют неизменяемую версию (ADR-013).
    boolean isActive();
    void markActive();
}

public interface ItemLease extends AutoCloseable {
    Item item();
    void close();   // снимает удержание; блок освобождается при нулевом счётчике
}
```

```java
package ru.octomem.engine;

public interface GetResult extends AutoCloseable {
    boolean found();
    Item item();     // null, если не найдено
    void close();    // снимает удержание
}
```

Запись целиком (заголовок фиксированного размера, ключ и значение) размещается в одном блоке распределителя вне кучи Java. В куче Java остаются только хеш-таблица со ссылками, неизменяемые метаданные версии и небольшие изменяемые служебные структуры. Размер блока равен `заголовок + ключ + значение + выравнивание`; именно он сравнивается с `item.maxSize`. Значение не копируется в отдельный объект Java.

**Неизменяемая опубликованная версия ([ADR-013](adr/ADR-013-immutable-published-item-version.md)).** Ключ, флаги, срок, токен `cas` и байты значения опубликованной записи неизменяемы. Любое изменение (`set`, `add`, `replace`, `append`, `prepend`, `cas`, `incr`, `decr`, `touch`, `gat`/`gats` в части срока) выполняется по схеме allocate → publish → retire: сначала выделяется и заполняется новая версия, затем она публикуется атомарной заменой ссылки, и только после этого старая версия выводится из обращения. Байты старой версии не перезаписываются; начатое чтение не видит промежуточного состояния. Позиция в LRU и счётчик удержаний — отдельное изменяемое служебное состояние, не входящее в неизменяемую версию. При нехватке памяти публикация не происходит: старая версия остаётся целой и видимой, клиент получает ошибку без частичной замены. Семантика токена `cas` при `touch`/`gat` остаётся по нормативному правилу смены версии при изменении записи и по эталону и здесь не переопределяется.

**Удержание и снимок ([ADR-016](adr/ADR-016-bounded-command-snapshots.md)).** Снимок удерживает все найденные уникальные версии до идемпотентного `close`, не более одного удержания каждой версии на снимок. Захват выполняется под всеми уникальными затронутыми segment locks в порядке индекса, с одним `capturedClock` для TTL и согласованной видимостью `flush_all`; все pin получены до unlock, промахи фиксированы. Сеть и callbacks под locks запрещены. Курсор сериализует одно значение за раз, но это не ограничение числа удержанных версий. Retired-блок остаётся в `memory.limit` до нулевого refcount; изменение, удаление, expiry и eviction не меняют его байты. Записи не ждут сокета: атомарный резерв замены либо OOM без частичного состояния. Удержание теперь зависит от набора снимка и ограничено native-бюджетом и допуском метаданных, а не прежним обещанием одной записи.

```java
package ru.octomem.engine;

public interface RetrievalSnapshot extends AutoCloseable {
    long capturedClock();
    Iterator<Item> values(); // один курсор, заимствованные Item, без дублей/промахов
    void close();           // идемпотентно: все refs и резерв метаданных
}
```

`RetrievalSnapshot` принадлежит `engine`, использует существующее ребро к `storage` и не меняет граф ADR-014. Курсор не выполняет новых поисков, не получает собственных lease и не освобождает Item. `Item` действителен до закрытия снимка. До успешной передачи `Response` снимком владеет вызывающий код и закрывает его при отказе передачи. `snapshotAndTouch` готовит все новые версии и резервы до публикации под всеми locks; отказ освобождает неопубликованное без TTL/CAS-изменений любого исходного ключа, дубли обновляются один раз. Публикация не выделяет память и не может отказать по ёмкости. Конкурирующие expiry/eviction/flush соблюдают ту же границу видимости (ADR-016 §4).

Токен `cas` — беззнаковое 64-битное число. Внутри он может храниться в `long`, но при разборе и выводе в протоколе обязан обрабатываться как беззнаковый. Счётчик версий при переполнении заворачивается по модулю `2^64`; уникальность в пределах процесса для практически значимого числа операций сохраняется и проверяется тестом.

### 4.6. Протокол

```java
public enum CommandType {
    GET, GETS, GAT, GATS, SET, ADD, REPLACE, APPEND, PREPEND, CAS,
    DELETE, INCR, DECR, TOUCH, FLUSH_ALL, STATS, STATS_ITEMS, STATS_SLABS,
    STATS_RESET, VERSION, VERBOSITY, QUIT
}

public interface Command {
    CommandType type();
    KeySequence keys();    // чтение: 1+; команды с ключом: 1; без ключа: size()==0
    int flags();
    long exptime();
    byte[] value();        // null, если не применимо
    long casId();          // cas: ожидаемая версия; gets/gats: не используется
    long delta();          // incr/decr: беззнаковая 64-битная дельта
    int level();           // verbosity: уровень
    boolean noreply();
}

public enum ResponseKind {
    RETRIEVAL, STORED, NOT_STORED, EXISTS, NOT_FOUND, DELETED, TOUCHED,
    OK, RESET, NUMBER, STATS, VERSION, ERROR, CLIENT_ERROR, SERVER_ERROR
}

public interface Response {
    ResponseKind kind();
    // Для RETRIEVAL: уже захваченный снимок целой команды; иначе null.
    RetrievalSnapshot snapshot();
    boolean includeCas();     // true для gets/gats — в VALUE добавляется токен версии
    long number();            // для NUMBER
    String text();            // для VERSION, CLIENT_ERROR, SERVER_ERROR
    List<String> statsLines();// для STATS
    void close();             // идемпотентно закрывает весь снимок
}

public interface ProtocolDecoder {
    void append(ByteBuffer input);
    // Возвращает следующую готовую команду или null, если данных недостаточно.
    Command nextCommand() throws ProtocolException;
}

public interface ProtocolEncoder {
    // Вызывается один раз на команду; возвращает возобновляемый писатель ответа.
    ResponseWriter encode(Response response);
}

public interface ResponseWriter {
    // Продвигает ответ, пока в приёмнике есть место. COMPLETE — ответ передан целиком.
    WriteStatus writeMore(ChunkSink sink);
    // Отменяет ответ и идемпотентно закрывает весь снимок.
    void close();
}

public enum WriteStatus { IN_PROGRESS, COMPLETE }

public interface ChunkSink {
    // Сколько байт можно принять прямо сейчас; 0 — приёмник заполнен.
    // Полная ёмкость приёмника не меньше 2 байт: иначе \r\n не передать
    // без разрыва. Постоянная ёмкость 1 недопустима (ADR-015).
    // При временной ёмкости 1 можно записать один обычный байт, но не
    // половину терминатора \r\n.
    int remainingCapacity();
    void accept(ByteBuffer chunk);
}
```

`Command` содержит разобранный тип и аргументы. `keys()` возвращает заимствованную `KeySequence`: для чтения (`get`, `gets`, `gat`, `gats`) size()≥1; для команд с ключом (`set`, `add`, `replace`, `append`, `prepend`, `cas`, `delete`, `incr`, `decr`, `touch`) size()==1; для команд без ключа (`flush_all`, `stats*`, `version`, `verbosity`, `quit`) size()==0. Материализация списка ключей не требуется и в production запрещена контрактом M2.

`Response` владеет заранее допущенным и полностью захваченным `RetrievalSnapshot`. Кодировщик получает один курсор `snapshot().values()` и выдаёт `VALUE ...`, значение и `END` без повторного чтения таблицы. Найденные ключи выводятся один раз в порядке первого появления; промахи пропускаются. `includeCas()` истинно для `gets`/`gats`. Писатель закрывает весь снимок при COMPLETE, отмене, ошибке, disconnect и shutdown, включая невыданные записи. После закрытия очереди транспорта содержат только собственные ограниченные копии частей под outbound-резервом по ADR-016 §3; ссылки на освобождённые native-блоки запрещены.

Соответствие аргументов типу команды задаётся нормативно:

| CommandType | `keys()` | `flags()` | `exptime()` | `value()` | `casId()` | `delta()` | `level()` |
|---|---|---|---|---|---|---|---|
| `get`, `gets` | 1+ | — | — | — | — | — | — |
| `gat`, `gats` | 1+ | — | срок | — | — | — | — |
| `set`, `add`, `replace` | 1 | флаги | срок | значение | — | — | — |
| `append`, `prepend` | 1 | — | — | значение | — | — | — |
| `cas` | 1 | флаги | срок | значение | версия | — | — |
| `delete` | 1 | — | — | — | — | — | — |
| `incr`, `decr` | 1 | — | — | — | — | дельта | — |
| `touch` | 1 | — | срок | — | — | — | — |
| `flush_all` | пусто | — | задержка | — | — | — | — |
| `stats*`, `version`, `quit` | пусто | — | — | — | — | — | — |
| `verbosity` | пусто | — | — | — | — | — | уровень |

Неиспользуемые аргументы не определены; реализации не должны на них полагаться. Необязательный устаревший `<time>` у `delete` поглощается декодером и в `Command` не переносится. `Response.number()` для `incr`/`decr` форматируется как беззнаковое 64-битное число.

Значение читается сегментами: кодировщик хранит смещение чтения в своём состоянии и вызывает `Item.readValue(offset, dst)`, увеличивая смещение на число прочитанных байт. Каждый ответ имеет собственное смещение без общего курсора внутри `Item`. `Command`/`Response` принадлежат одному соединению и его циклу событий, не передаются между потоками; состояние незавершённого ответа сохраняется между вызовами `writeMore` в пределах допущенного снимка и бюджетов ADR-016.

**Контракт разбора.** `nextCommand` возвращает ровно одну готовую команду за вызов и `null`, если данных недостаточно. Декодер не хранит состояние, кроме буфера незавершённой команды, и не имеет права декодировать больше запрошенного. Транспорт вызывает `nextCommand` не более `connections.maxInflightCommands` раз для незавершённых команд и прекращает чтение из сокета, когда предел достигнут.

**Контракт возобновляемой записи.**

- `encode` вызывается один раз и возвращает `ResponseWriter` с сохранённым положением внутри ответа.
- `writeMore` сам определяет размер следующей части: не более `min(remainingCapacity(), protocol.maxChunkBytes)` и без разрыва последовательности `\r\n`.
- Полная ёмкость приёмника не меньше 2 байт; постоянная ёмкость 1 байт недопустима и отвергается при настройке приёмника до начала записи. `protocol.maxChunkBytes` имеет допустимый минимум 2 байта (значение по умолчанию `64k` не меняется) ([ADR-015](adr/ADR-015-chunk-sink-crlf-capacity.md)).
- При `remainingCapacity() == 0` `writeMore` возвращает `IN_PROGRESS`, не записывая ничего. При `remainingCapacity() == 1` разрешено записать один обычный байт, не входящий в `\r\n`, но потребить `\r` или `\n` терминатора нельзя: если следующая часть — `\r\n`, `writeMore` возвращает `IN_PROGRESS`, не записывая половину терминатора.
- Приёмник обязан дренироваться и снова дать достаточную ёмкость, либо транспорт ждёт `OP_WRITE` и вызывает снова; занятое ожидание (spin) в цикле событий запрещено.
- `writeMore` возвращает `COMPLETE` ровно после передачи последней части. Повторный вызов после `COMPLETE` запрещён; начать ответ заново нельзя.
- `close` вызывается также при COMPLETE, отмене, закрытии соединения, ошибке и shutdown; идемпотентно закрывает снимок и освобождает все удержания и метаданные.

Значение передаётся сегментами из блока распределителя без полной промежуточной копии. Сериализованный ответ не материализуется целиком; при этом суммарные удерживаемые версии могут занимать объём всего набора снимка в пределах native memory.limit. Отсутствие полной копии не означает независимость удержания от размера ответа (ADR-016).

## 5. Модель потоков

```text
Поток-акцептор (1)
   |
   +--> цикл событий 1 --- соединения A, D, G
   +--> цикл событий 2 --- соединения B, E, H
   +--> цикл событий N --- соединения C, F, I

Фоновые потоки:
   - обслуживание LRU и вытеснение
   - активная очистка просроченных записей
```

- Одно соединение закреплено за одним циклом событий.
- Команды одного соединения исполняются строго по порядку.
- Число циклов по умолчанию — `2 × доступные процессоры`, но не менее двух; настраивается.
- Запись ответа не блокирует цикл: используется очередь исходящих частей и интерес на запись.
- Частичная запись обрабатывается через `OP_WRITE`.
- `connections.pendingWriteBytes` ограничивает **объём подготовленных, но ещё не записанных байтов** на соединение. Это не предел размера ответа. Пока лимит не достигнут, кодировщик выдаёт следующие части; при достижении — транспорт приостанавливает выборку частей (backpressure) и возобновляет её по `OP_WRITE`.
- `connections.maxInflightCommands` ограничивает число декодированных, но не завершённых команд на соединение. Транспорт прекращает чтение из сокета, когда достигнут этот предел или заполнена исходящая очередь, и возобновляет чтение после их опустошения. Так глубокий конвейер от медленного клиента не накапливает команды и удерживаемые записи.
- Остановившийся читатель не увеличивает память сверх лимита: очередь не растёт. Если задан `connections.idleTimeoutSeconds`, такое соединение закрывается по тайм-ауту; по умолчанию тайм-аут выключен, и соединение простаивает в пределах лимита.
- Движок потокобезопасен за счёт блокировок по сегментам хеш-таблицы, а не глобальной блокировки.

Обработка большой команды чтения или записи не должна блокировать цикл: разбор и копирование выполняются в пределах цикла, но без ожидания.

Большой multi-get передаётся потоково из ограниченного снимка; его native-версии удерживаются независимо от одного курсора. Допуск метаданных до первого байта, отказ даёт известный SERVER_ERROR без частичного VALUE. Каждое соединение имеет собственную заранее зарезервированную transmit lane 512 байт для нормальных/ошибочных ответов; общий burst pool необязателен. Body admission резервирует весь payload до чтения, а при отказе немедленно выбирает OOM и drain через собственную receive/discard lane 512 байт, не ждёт с частичным телом. Pipeline ограничен `connections.maxInflightCommands`, исходящие payload-байты обеих lane/burst соблюдают `connections.pendingWriteBytes`; готовые соединения обслуживаются round-robin без spin и unlimited callbacks. Полный контракт F1/F2 в ADR-016 §5. Тайм-ауты не меняются: при 0 медленный клиент может удерживать свой ограниченный снимок/полный body reserve до disconnect/shutdown, не лишая здорового клиента его lane.

## 6. Модель памяти

- **Записи** целиком хранятся в ограниченных страницах вне кучи Java. На основной OpenJDK 25 допускается стабильный FFM (MemorySegment/Arena) либо direct ByteBuffer; backend фиксируется до T-009 по прототипу и контракту владения. ByteBuffer для NIO не определяет способ выделения памяти.
- **Куча Java** хранит хеш-таблицу, служебные структуры и ограниченные временные входные/исходящие буферы; постоянные значения кеша находятся вне кучи. Временный `byte[]` команды не является вторым постоянным хранилищем.
- **Хеш-таблица** хранит ссылки на записи и не дублирует значения.
- **Предел памяти** контролируется распределителем; при нехватке сначала вытесняются давно неиспользуемые записи, затем возвращается `OUT_OF_MEMORY`.
- **Размер записи** ограничен настройкой `item.maxSize`. Предел применяется к полной записи (ключ, служебные поля, значение), как у эталона. Превышение даёт `SERVER_ERROR object too large for cache` по спецификации 04.

Потребление RSS измеряется в испытаниях и публикуется в эксплуатационном паспорте. Запрещено обещать отсутствие накладных расходов JVM.

**Совокупные бюджеты ADR-016 (проект, F1/F2/F3).** Native-страницы и резерв будущих страниц не превышают `memory.limit`; live/retired/retained/reserved-блоки учтены без двойного счёта. Отдельные heap-пулы: snapshot `min(floor(memory.limit / 16), 16 MiB)` с checked платой `512 + 512 * N`, body ingress `max(item.maxSize + 32, min(memory.limit, 64 MiB))`, control `544 * 2 * connections.max`, необязательный outbound burst `min(memory.limit, 64 MiB)`. Все вычисления checked long до allocation, каждый reserve атомарен; передача владения сохраняет учёт, release/cancel/error/disconnect/shutdown возвращают резерв ровно один раз. Пулы не ограничивают RSS, четырнадцать публичных настроек/defaults не меняются.

Body payload плюс 32 резервируется целиком до allocation/bodyread, один byte[] точной длины без роста/old+new. Отказ сразу выбирает OOM: допустимый объявленный payload и CRLF отбрасываются через собственную scratch lane до ошибки/продолжения pipeline; правильный noreply подавляет ответ, malformed terminator закрывает невосстановимый поток по 04. Частичные отправители удерживают уже допущенные полные резервы, но не создают цикл ожидания недостающей памяти. Eager itemMax на каждое соединение запрещён; любой допустимый настроенный item помещается один в пустой body pool, включая >64 MiB.

До регистрации каждого соединения резервируются собственные byte[512] receive/discard и byte[512] transmit, по 544 логических байта с overhead32; allocation ленивый, failure возвращает резерв и безопасно отклоняет соединение. Transmit обслуживает нормальные ответы/ошибки/stats частями `min(512, protocol.maxChunkBytes)` без обязательного burst-пула; CRLF2 возможен даже при memory.limit=1. Форматирование ограничено lane; здоровое соединение не ждёт чужую очередь. Round-robin готовых/ожидающих с конечным бюджетом без busyloop; собственный заполненный transmit даёт локальное backpressure, не поздний OOM допуска. Строка ограничена maxLine; байты строки/ключей и публичные defensive copies тоже имеют ограниченный входной/control-учёт, не скрытую копию тела.

Снимок имеет ровно шесть массивов: `Item reference[N]`, `int firstOccurrenceOrder[N]`, `int segmentIds[N]`, `int dedupOrder[N]`, `byte keyLengths[N]` (unsigned длина), `byte keys[250*N]`; N включает дубли/промахи, ключ максимум250. Нет объектов на ключ, роста или массивов по общему числу сегментов; итеративный in-place heapsort индексов, segment IDs compact в том же массиве, постоянный scratch включён в плату. Внутренний захват использует bounded borrowed key view под lock до pin, не `Item.key()` defensive copies. При предположениях ссылки≤8 и заголовка массива с выравниванием≤64 payload=271N≤512N, шесть заголовков=384, фиксированные wrapper/курсор/scratch≤128, всего≤512+512N. Проверить HotSpot layout на целевой JDK25, это не RSS-измерение. Малый snapshot cap может отказать до VALUE, но control lane остаётся рабочей.

Порядок locks: sorted segments → allocator mutex → LRU metadata. Allocator под захваченным набором не берёт новый segment lock и не вытесняет; eviction preflight отдельно после unlock с исключением целевых ключей, затем полный повторный захват/проверка с новым capturedClock. Flush/expiry соблюдают общую видимость. Никаких I/O/queue waits под locks; writer/курсор/close confined циклу событий, shutdown передаёт отмену. Allocation failure и reserve-cancel освобождают полученное, не обещая восстановление после произвольного JVM OOME. Реальные heap/native/RSS и p99 измеряются прототипом (ADR-016 §5).

## 7. Модель ошибок

**Полный heap-учёт, M1/M2.** Пятый pool line/descriptor: `charge = 2L * L + 256`, `perconn = satMul(maxInflight, charge)`, `global = satMul(connections.max, perconn)`, где L=protocol.maxLineBytes. Положительный satMul насыщает только LIMIT до Long.MAX_VALUE при переполнении; charge для int L помещается в long, actual charge/live counters не насыщаются. CAS reserve проверяет `charge <= limit - used` до сложения. Overflow теоретического LIMIT не отвергает конфигурацию и не урезает публичные пределы; реальная нехватка даёт resource admission failure, не startup rejection. Ceiling не выделяется eager. Slot reserve до чтения, full pipeline отключает OP_READ без body reserve ради slot; control продолжает ответы. При snapshot handoff оба резерва учтены на пике до release line.

```java
package ru.octomem.engine;

public interface KeySequence {
    int size(); // один линейный scan, без per-key allocation
    // Backing immutable и borrowed до command release; visitor не удерживает его далее.
    void forEachKey(KeyVisitor visitor); // последовательный borrowed pass
}

public interface KeyVisitor {
    void accept(byte[] backing, int offset, int length);
}
```

Protocol реализует engine.KeySequence по существующему ребру, без новых util-зависимостей. Backing raw line неизменяем до command release; visitor не изменяет его и не сохраняет за этой границей. Нет per-key arrays/views/List, starts/offset arrays, byte[] getKey или рекурсии. Size и forEachKey выполняют линейные последовательные проходы, не O(N²) indexed rescans. Парсер имеет один примитивный курсор; raw backing геометрически растёт до L с old+new payload≤2L, максимум два header/alignment по64 плюс parser/sequence wrapper/cursor≤128 внутри charge256. После разбора логическая длина≤L, shrink-copy отсутствует; допустим ленивый exact-L backing при реальном resource admission. Сначала count N, затем snapshot reserve, затем allocation шести массивов и sequential fill keys[250N]; дедупликация/first occurrence только индексами снимка. Public defensive Item.key() copy учтена отдельно line/control, не используется внутренним snapshot; необязательный List adapter только тестовый вне production-бюджета. Все пять heap-пулов отдельно от native, layout и RSS/пики измеряются, четырнадцать defaults сохранены.

| Источник | Класс | Ответ клиенту |
|---|---|---|
| Неизвестная команда | Протокол | `ERROR` |
| Неверные аргументы команды | Протокол | `CLIENT_ERROR <текст>` |
| Превышение размера значения | Протокол | `SERVER_ERROR object too large for cache` |
| Нехватка памяти | Движок | `SERVER_ERROR out of memory storing object` |
| Восстановимый отказ выделения (`CacheCapacityException`) | Движок | `SERVER_ERROR out of memory storing object` |
| Ошибка чтения данных | Протокол | `CLIENT_ERROR bad data chunk` |
| Внутренняя ошибка | Движок | `SERVER_ERROR <текст>` |

Внутренние исключения не должны завершать процесс. Неизвестная команда не меняет состояние кеша. `CacheCapacityException` при допуске снимка чтения или подготовке `touch`/`gat`/`gats` даёт `SERVER_ERROR out of memory storing object` до первого байта ответа; состояние и TTL/CAS всех исходных ключей сохраняются, резервы и удержания освобождаются. Подавление по `noreply` действует только у `touch`. Multi-gat использует prepare-all-before-publish и полный откат по принятому ADR-016; R-04 закрыт как DESIGN finding, проверка реализации обязательна. После начала ответа нехватка исходящего буфера вызывает только backpressure, не поздний отказ допуска. Точные строки заданы в 04.

**Проверка конфигурации.** `protocol.maxChunkBytes` обязан быть не меньше 2 байт (значение по умолчанию `64k` не меняется); значение меньше 2 отвергается с понятной ошибкой до запуска. Значения по умолчанию не должны неожиданно менять поведение известных клиентов.

## 9. Наблюдаемость

- Команда `stats` отдаёт счётчики соединений, команд, попаданий и промахов, памяти и вытеснений.
- `stats items` и `stats slabs` отдают сведения по классам и наборам.
- Журнал пишет запуск, конфигурацию, ошибки, остановку, предупреждения о нехватке памяти.
- Журнал не содержит значений кеша и ключей по умолчанию.
- Снимок `stats` используется для испытаний памяти и нагрузки.

## 12. Тактики качества

| Атрибут | Тактика |
|---|---|
| Совместимость | Конформные тесты против эталона, перечень отличий, пилоты |
| Производительность | Неблокирующий ввод-вывод, блокировки по сегментам, отсутствие лишних копий |
| Память | Прямые буферы, классы размеров, ограничение записи, вытеснение |
| Надёжность | Изоляция соединений, отказ от падений на неверном вводе, фоновые потоки без глобальных блокировок |
| Сопровождаемость | Фиксированные интерфейсы, тест архитектуры, обязательный ADR |
| Безопасность | Привязка к локальному адресу, отсутствие сети наружу, лимиты буферов |
