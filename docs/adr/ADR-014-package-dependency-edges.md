# ADR-014. Рёбра зависимостей пакетов и владение типами

**Статус.** ПРИНЯТО (accepted) координатором 15.09.2026: принят **точный существующий граф `docs/03` без изменения рёбер**; R-07 закрыт scoped-приёмкой T-001. ADR-013 и ADR-015 остаются ПРЕДЛОЖЕНО, R-04/R-09 открыты, T-004 не заморожен. Принятие фиксирует архитектурный граф, а не реализацию и не релизную готовность.

**Дата.** 14.09.2026.

**Контекст.** [R-07](../review-2026-09-14.md): правило зависимостей `docs/03` разрешало только рёбра таблицы, но ни одному потребителю обязательного `Clock` не разрешался `util`; кроме того, не было определено, какому пакету принадлежат `Item`/`ItemLease`/`GetResult`. Без этого обязательный архитектурный тест Т-02 отверг бы корректную реализацию, а `protocol`, читающий значение через `GetResult.item()`, формально зависел бы от `storage` без разрешённого ребра.

## Решение

### 1. Владение типами

| Тип | Пакет |
|---|---|
| `Item`, `ItemLease` | `ru.octomem.storage` |
| `SlabHandle`, `MemoryAllocator` | `ru.octomem.storage` |
| `SlabClassStats` | `ru.octomem.stats` |
| `GetResult`, `StoreResult`, `CounterResult`, `CacheEngine`, `CacheCapacityException` | `ru.octomem.engine` |
| `ProtocolDecoder`, `ProtocolEncoder`, `ResponseWriter`, `ChunkSink`, `WriteStatus`, `Command`, `CommandType`, `Response`, `ResponseKind` | `ru.octomem.protocol` |
| `Clock` | `ru.octomem.util` |

`GetResult.item()` возвращает `ru.octomem.storage.Item`; сигнатуры `storage` и `engine` согласованы между собой, дублирующие типы `Item`/`GetResult` в других пакетах запрещены.

### 2. Разрешённые рёбра (один ациклический граф)

| Пакет | Зависит от |
|---|---|
| `ru.octomem.transport` | `protocol`, `engine`, `storage`, `stats`, `util` |
| `ru.octomem.protocol` | `engine`, `storage`, `stats`, `util` |
| `ru.octomem.engine` | `storage`, `expiry`, `eviction`, `stats`, `util` |
| `ru.octomem.storage` | `stats`, `util` |
| `ru.octomem.expiry` | `storage`, `stats`, `util` |
| `ru.octomem.eviction` | `storage`, `stats` |
| `ru.octomem.stats` | — (только JDK) |
| `ru.octomem.config` | — (только JDK) |
| `ru.octomem.cli` | все (композиция; рёбра не меняются) |
| `ru.octomem.util` | — (только JDK) |

### 3. Правила

- Прямое ребро `protocol → storage` разрешено и обосновано: кодировщик читает значение сегментами через `Item.readValue` и удерживает `ItemLease`; типы не дублируются.
- `util` можно использовать только из `engine`, `storage`, `expiry`, `transport`, `protocol` и только для чистых утилит (`Clock`, хеширование, работа с байтами). `util` не зависит ни от чего, кроме JDK.
- **`stats` — авторитетная строка «только JDK».** `stats` не входит в число потребителей `util` и не получает других проектных зависимостей; таблица рёбер выше является источником истины.
- **Обратные рёбра запрещены.** `util` и `stats` не зависят от других пакетов проекта; цикл недопустим.
- Рёбра `config`, `cli`, `eviction` сохраняются как прежде. `config` остаётся без проектных зависимостей; `cli` — композиционный корень; `eviction` использует `storage` и `stats` и не получает `util` этим ADR.
- Нарушение проверяется сборкой и архитектурным тестом Т-02 на точном графе выше.

## Обоснование

Единый граф устраняет противоречие R-07, не расширяя права: `util` становится явно разрешённым листовым пакетом для фактических потребителей часов и хеша, а `protocol` получает ровно одно осознанное ребро к `storage` для сегментного чтения значения. Закрытые обратные рёбра и листовые `util`/`stats` сохраняют ацикличность и тестируемость границ.

## Последствия

- Т-001 архитектурный тест и T-004 фиксируют именно этот DAG.
- Появление новой зависимости (например `eviction → util`) требует нового ADR, а не молчаливого расширения таблицы.
- Трассировка: `NFR-30`, docs/03 §3, T-001, T-004, T-007, T-009, TEST-01.

- **R-07 закрыт** по независимой проверке графа и двум scoped-прогонам T-001 (Windows и Linux, по 121 тесту, ноль отказов/ошибок/пропусков).

## Не решается этим ADR

- **R-04 остаётся открытым:** ребро `protocol → storage` не превращает multi-get в снимок нескольких ключей.
- **R-09 отложен:** граф не вводит бюджетов памяти.
