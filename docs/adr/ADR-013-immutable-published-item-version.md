# ADR-013. Неизменяемая опубликованная версия записи

> **Уточнение 25.10.2026:** правила неизменяемости и удержаний сохраняются. Общие формулировки ниже о смене CAS и сохранении старого значения при отказе выделения уточнены [docs/04, коррекция 0.4](../04-protocol-compatibility-specification.md): TTL-only обновления сохраняют wire-CAS, ранний отказ выделения записи SET инвалидирует старый ключ. [ADR-019](ADR-019-wire-cas-and-set-failure.md) отделяет внешний CAS от внутреннего владения; ожидает независимого ревью. Реализация и новые тесты NOT_RUN.

**Статус.** ACCEPTED координатором 15.09.2026 после независимого ревью без замечаний `97c8c23b86be`, совместно с ADR-015/016. R-05 закрыт как DESIGN finding; R-04/R-08/R-09 также закрыты как проектные замечания, R-07 уже закрыт. Разрешена реализация интерфейсов T-004, но задача не объявляется выполненной или замороженной до её приёмки. Это не PASS реализации, испытаний, производительности или релиза. Прежние статусы в описании правок и разделе «Не решается этим ADR» ниже исторические; текущее решение по R-04/R-09 находится в принятом ADR-016.

**Дата.** 14.09.2026.

**Контекст.** [R-05](../review-2026-09-14.md): `docs/03` защищал удержанный блок от освобождения, но не от изменения, а `docs/05` запрещал промежуточное состояние при чтении. Потоковый `get` мог увидеть смесь байтов и метаданных, если удержанная запись изменялась на месте (`incr`, `append`, `replace`, `touch`). Нужен явный контракт неизменяемой версии под удержанием.

## Решение

1. **Опубликованная версия неизменяема.** После публикации записи в хеш-таблице её ключ, флаги, срок жизни, токен `cas` и байты значения образуют неизменяемую версию. Ни одно из этих полей не изменяется на месте.
2. **Обновление — это allocate → publish → retire.** Любое изменение (`set`, `add`, `replace`, `append`, `prepend`, `cas`, `incr`, `decr`, `touch`, `gat`/`gats` в части срока) сначала выделяет новый блок и новую версию, затем публикует её атомарной заменой ссылки в хеш-таблице, и только после этого помечает старую версию выведенной из обращения. Байты старой версии не перезаписываются.
3. **Освобождение старой версии — после нуля удержаний.** Блок выведенной версии освобождается и переиспользуется только когда счётчик удержаний (`ItemLease`/refcount) достигает нуля. Удаление, замена, просрочка и вытеснение не освобождают блок под удержанием.
4. **LRU и счётчик удержаний — отдельное изменяемое служебное состояние.** Позиция в LRU и refcount не входят в неизменяемую версию и хранятся в отдельной синхронизированной служебной структуре, связанной с блоком. `Item.isActive()`/`Item.markActive()` обращаются к этому служебному состоянию и **никогда** не меняют ключ, флаги, срок, `cas` или значение.
5. **Ключ не отдаёт записываемые хранимые байты.** `Item.key()` возвращает либо защитную копию, либо явно ограниченное представление только для чтения. Прямой доступ к изменяемым хранимым байтам ключа запрещён. Значение доступно только сегментно через `Item.readValue(offset, dst)`; метода, возвращающего записываемый массив значения, нет.
6. **Смещение чтения — локально у читателя.** Каждый ответ/читатель хранит своё смещение и не использует общий курсор внутри `Item`. Конкурентное чтение одной версии разными соединениями безопасно.
7. **OOM сохраняет старое состояние.** Если выделение новой версии (или её запись) не удалось, публикация не происходит: прежняя версия остаётся целой и видимой, клиент получает `OUT_OF_MEMORY` (или `SERVER_ERROR` по `docs/04`) без частичной замены и без повреждения записи.

## Проверяемый отказ ёмкости (`CacheCapacityException`) — уточнение по findings

`touch` и `getAndTouch`/`gat`/`gats` изменяют срок, а значит публикуют новую версию. Восстановимый отказ выделения на этом пути сигнализируется **проверяемым** `CacheCapacityException` пакета `ru.octomem.engine` (ADR-014), объявленным в сигнатурах `throws`. Отказ нельзя кодировать значением `false` (`touch`) или промахом/`null` (`getAndTouch`): `false` и ненайденное значение означают иное.

- Тип несёт только ограниченные метаданные (например, требуемый размер блока и предел) и не содержит свободных текстов внутренних ошибок.
- Движок отображает исключение в определённый ответ `SERVER_ERROR out of memory storing object`; при **явной** лексеме `noreply` ответ подавляется только у `touch`. `gat`/`gats` — команды чтения без `noreply` и всегда отвечают, а лексема `noreply` в них является обычным ключом.
- При исключении состояние не меняется: запись, её срок и токен `cas` остаются прежними, а все уже взятые удержания (`ItemLease`/`GetResult`) освобождаются.
- Для multi-`gat`/`gats` восстановимый отказ ёмкости не должен частично применять обновление ни к одному ключу. Это требование атомарности по всем ключам; реализация здесь не проектируется, **R-04 остаётся открытым**.
- Точное совпадение строки ошибки с зафиксированным эталоном проверяется дифференциальным тестом; формулировка не выводится из текста исключения.

## Обоснование

Неизменяемая версия делает видимость по ключу атомарной: читатель под удержанием всегда видит одну согласованную версию, а обновитель не может изменить байты под ним. Разделение неизменяемого содержимого и изменяемого служебного состояния (LRU, refcount) сохраняет дешёвую отметку активности без гонки с потоковой выдачей. Ограничение доступа к хранимым байтам исключает случайную порчу записи через возвращённый массив.

## Последствия

- `incr`/`decr`/`append`/`prepend`/`touch` требуют нового выделения и могут отказать по памяти; при отказе старое значение сохраняется.
- Отметка активности и удержания не входят в блок значения и не могут изменить выдаваемые байты.
- Смена токена `cas` при `touch`/`gat` остаётся по действующему нормативному правилу смены версии при изменении записи ([ЧТЗ-05-R02](../05-detailed-technical-specifications.md)) и по эталону; этот ADR не переопределяет семантику `cas` для `touch`.
- Трассировка: `FR-40`…`FR-43`, `NFR-13`, ЧТЗ-02-R19, ЧТЗ-03-R13/R14, ЧТЗ-05-R02/R09/R11/R12/R13, docs/04 §3.3/§5.3/§7/§8, docs/06 Т-02/Т-04, T-004, T-009, T-011, TEST-01, TEST-06.
- Правка 0.2 (findings): добавлен проверяемый `CacheCapacityException` для `touch`/`getAndTouch` и требование атомарности multi-gat; обновление документации ещё не принято независимым ревью. Правка 0.3: `gat`/`gats` не поддерживают `noreply` и всегда отвечают.

## Не решается этим ADR

- **R-04 остаётся открытым.** Здесь зафиксирована неизменяемость одной версии по ключу, а не атомарный снимок нескольких ключей в одном multi-get. Требование `FR-40` не сужается и не расширяется.
- **R-09 отложен.** Бюджеты памяти и новые значения по умолчанию не вводятся.
