# ADR-019. Wire-CAS, внутренние версии и отказ SET

**Дата:** 25.10.2026. **Статус:** ACCEPTED координатором после независимого ревью `ctx_d5ab24e0309e`: разграничение wire-CAS/владения и фазовая инвалидация SET приняты как дизайн. Ранее PROPOSED/NOT_RUN относились к моменту создания. Реализация имеет 128 прошедших целевых регрессий, но полная приёмка и исправление дополнительной числовой грамматики ещё проверяются; актуальные идентичности и ограничения — в checkpoint `run_fb08f2b2d70d`. Это не приёмка продукта или релиза.

## Контекст

Сверка с Memcached 1.6.45 обнаружила два неверных обобщения в ADR-013: внутреннюю версию нельзя отождествлять с CAS протокола, а сохранение прежнего значения при любом отказе выделения не соответствует SET эталона. Основания и сценарии — [F2/F3](../compatibility-recheck-2026-10-25.md). Нормативные уточнения сначала внесены в [docs/04](../04-protocol-compatibility-specification.md).

## Решение

1. Сохраняются неизменяемые опубликованные версии, ограниченные снимки, порядок блокировок и освобождение после последнего удержания. Ни одна правка совместимости не разрешает изменять байты под читателем.
2. CAS — внешняя семантика условной записи, а не идентификатор физического блока. Успешный `touch`/`gat`/`gats` может публиковать новый блок с прежним wire-CAS. Логика владения не должна использовать равенство CAS как доказательство тождества двух блоков. Изменения данных сохраняют действующий механизм выдачи нового CAS.
3. Отказ выделения записи в корректном SET из-за размера или ёмкости инвалидирует прежнюю запись по ключу. Уже захваченные снимки продолжают владеть старой версией; новые чтения её не получают. Физическое освобождение по-прежнему отложено до нуля удержаний.
4. Инвалидация — атомарная операция над индексом под обычной блокировкой ключа. Передача или отбрасывание сетевого тела не выполняются под блокировкой. Сетевые команды одного соединения сохраняют порядок. Точный момент инвалидации и допустимый порядок с конкурентным SET должны быть проверены относительно фазы отказа эталона; нельзя удалить новую запись от другого писателя поздним callback по устаревшей ссылке.
5. Исключение SET узкое: не заменяет rollback для CAS, add, replace, append/prepend, счётчиков и multi-gat. Malformed-заголовок не инвалидирует запись. Отказы входного heap-admission и позднего чтения тела требуют отдельного фазового оракула; общая строка OOM не доказывает эквивалентность native allocation отказу эталона.
6. Ошибки формируются по типу команды, фазе и причине, а не по произвольному тексту исключения. Для арифметического EOM — `SERVER_ERROR out of memory`, для начального выделения storage — `SERVER_ERROR out of memory storing object`. Отказ выделения/превышение размера объединённого append/prepend после допуска входного фрагмента даёт `NOT_STORED`, сохраняя прежнюю запись. Правила `noreply` и кадрирования сохраняются.

## Проверка и последствия

- Независимый тестировщик сначала фиксирует наблюдаемые ответы и состояние эталона 1.6.45, затем проверяет Octomem. Ревью тестов не заменяет независимое авторство.
- Нужны обычный сценарий TTL-only/CAS, отказ SET, negative controls для остальных storage-команд, фрагментированное тело, `noreply`, удержанный читатель и конкурентный писатель. Сырые ответы и хеши обязательны.
- Нельзя возвращать совместимость путём отказа от memory accounting, полного копирования ответа или удержания locks на socket I/O.
- Старые тесты, требовавшие нового CAS после touch или сохранения значения при раннем allocation-отказе SET, должны изменяться независимым автором по новому оракулу, а не под вывод реализации. Старые сырые результаты сохраняются.
- Никаких новых runtime-зависимостей, preview API, Java downgrade или переноса исходного кода Memcached. Самостоятельная Java-реализация по наблюдаемой семантике.
