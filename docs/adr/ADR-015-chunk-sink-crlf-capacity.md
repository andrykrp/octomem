# ADR-015. Ёмкость ChunkSink и неразрывный CRLF

**Статус.** ACCEPTED координатором 15.09.2026 после независимого ревью без замечаний `97c8c23b86be`, совместно с ADR-013/016. R-08 закрыт как DESIGN finding; R-04/R-05/R-09 также закрыты как проектные замечания, R-07 уже закрыт. Разрешена реализация интерфейсов T-004, не заявлены завершение/заморозка задачи или PASS реализации, испытаний, производительности и релиза. Прежние статусы в истории правок и разделе «Не решается этим ADR» ниже исторические; текущее решение по R-04/R-09 находится в принятом ADR-016. Правила CRLF и defaults не меняются.

**Дата.** 14.09.2026.

**Контекст.** [R-08](../review-2026-09-14.md): `docs/03` запрещал разрывать `\r\n`, но при ёмкости приёмника 1 байт не определял продвижение, поэтому писатель мог вечно возвращать `IN_PROGRESS` на терминаторе. Запрет разрыва `\r\n` также является критерием приёмки T-007 и не подлежит ослаблению или удалению.

## Решение

1. **Правило неразрывного `\r\n` сохраняется.** `ResponseWriter.writeMore` никогда не разрывает пару `\r` `\n` между двумя вызовами `ChunkSink.accept`.
2. **Полная ёмкость приёмника не меньше 2 байт.** Приёмник (`ChunkSink`) с постоянной общей ёмкостью 1 байт недопустим и должен отвергаться при настройке/создании до начала записи: таким приёмником нельзя передать `\r\n` без разрыва. Единица ёмкости — постоянная недопустимая конфигурация, а не временный остаток. Тот же минимум 2 применяется к настройке `protocol.maxChunkBytes` (значение по умолчанию `64k` не меняется); `maxChunkBytes < 2` отвергается при проверке конфигурации (D-02/T-002).
3. **Временная ёмкость 0 и 1.** При `remainingCapacity() == 0` `writeMore` возвращает `IN_PROGRESS` и ничего не записывает. При `remainingCapacity() == 1` разрешено записать один обычный байт, не входящий в `\r\n`, но потребить `\r` или `\n` терминатора нельзя: если следующая часть — `\r\n`, возвращается `IN_PROGRESS` без записи половины терминатора. Терминатор `\r\n` всегда передаётся целиком при ёмкости ≥ 2.
4. **Никакого активного ожидания.** Приёмник обязан дренироваться и снова предоставить достаточную ёмкость (не меньше 2 для `\r\n`), либо планировщик ждёт `OP_WRITE` и повторяет вызов. Занятое ожидание (spin) в цикле событий запрещено.
5. **Ни новых ключей, ни новых значений по умолчанию.** Значение `connections.pendingWriteBytes` по умолчанию `8m` уже ≥ 2. Это уточнение контракта приёмника, а не новый бюджет памяти; конкретные ключи конфигурации остаются за ЧТЗ-07/D-02.

## Обоснование

Правило «≥ 2 байта ёмкости для неразрывного CRLF» делает прогресс гарантированным без ослабления запрета разрыва: при постоянной ёмкости 1 байт невозможность корректной записи распознаётся как ошибка конфигурации, а при временном остатке 0/1 писатель не тратит байты и не крутит цикл. Это совместимо с существующим backpressure по `connections.pendingWriteBytes`.

## Последствия

- T-007 проверяет случаи ёмкости 0, 1 (недопустимая постоянная конфигурация) и 2, планирование по `OP_WRITE` без spin и недопустимость `protocol.maxChunkBytes < 2`; T-002 проверяет границу настройки.
- TEST-01 включает те же ёмкости и отсутствие расхода байт терминатора при ёмкости 1; docs/06 Т-02 — границы `maxChunkBytes`.
- Трассировка: docs/03 §4.6/§8, docs/06 Т-02, D-02, ЧТЗ-02-R16/R18, ЧТЗ-07-R11, T-002, T-004, T-007, TEST-01.
- Правка 0.2 (findings): временная ёмкость 1 может принять один обычный байт, но не половину `\r\n`; добавлен минимум `protocol.maxChunkBytes` 2; ещё не принято независимым ревью.

## Не решается этим ADR

- **R-04 остаётся открытым.**
- **R-09 отложен:** бюджеты памяти и новые значения по умолчанию не вводятся; валидация относится к объявленной ёмкости приёмника, а не к лимиту очереди.
