# План оптимизации производительности octomem

17.09.2026. Статус: **план будущих работ, не реализация и не аттестация производительности**. Архитектурные решения принимает координатор; изменения контрактов требуют ADR. Этот документ не разрешает запуск стенда, изменение конфигурации продукта или публикацию.

## Краткий вывод

Сначала получить валидную исходную линию на текущем кандидате, затем снять ограниченный профиль JFR. Первый небольшой кандидат: убрать сбор статистики страниц из поиска неизменяемого класса размера. Далее, если профиль подтверждает затраты, укрупнить ограниченные копирования/вывод, объединить короткие ответы pipeline, сократить временные объекты и лишь затем менять метаданные либо параметры JVM. Вытеснение и учёт статистики оптимизировать отдельными изменениями, только при подтверждённом вкладе.

В коде действительно есть scratch по 256 байт, транспортные буферы по 512 байт, общий monitor аллокатора на каждую копию, обход страниц внутри `classFor` и повторные ограниченные поиски жертвы. Это доказательство выполняемой работы, **не доказательство её доли во времени**. Нельзя заранее обещать выигрыш, достижимость или недостижимость M3, предел Java либо необходимость переписать архитектуру.

M1 ≥ 0,90, M2 ≤ 1,25, M3 по **полному RSS процесса** ≤ 1,20 эталона сохраняются для каждого обязательного сценария. Быстрее прежней версии не означает соответствовать эталону. Нулевые ошибки, корректные ответы, ограниченность ресурсов и справедливое обслуживание соединений обязательны независимо от скорости.

## Общие правила экспериментов

Термины: baseline означает исходную линию измерений; scratch = временный рабочий буфер; lane = собственный буфер соединения; admission = допуск после резервирования ресурса; lease/pin = удержание версии от освобождения; owner = единственный владелец ресурса; burst = дополнительный ограниченный буфер ускорения; backpressure = приостановка поступления работы при заполнении буфера; fairness = справедливое обслуживание клиентов. Имена методов и параметров оставлены как в коде.

Все последующие команды и эксперименты **предложены, здесь не выполнялись**. До каждой реализации записать один проверяемый механизм, один вариант изменения, исходный/новый SHA-256, ограничение времени/памяти и правило остановки. Для сравнения A/B использовать неизменённый A и ровно один изменённый B; отдельно сравнить каждый с эталоном. Не смешивать изменение кода, GC, размеров буферов и клиентского CPU в одном кандидате.

Фиксировать точную свободную сборку OpenJDK 25, patch/version, хеш Java/JAR/эталона/клиента/тестов/harness, flags, ОС, топологию CPU, affinity, фактические cgroup v2 `cpu.max`, `cpu.stat`, `cpuset.cpus.effective`, `memory.max`, `memory.current`, `memory.events` и настройки swap. `ActiveProcessorCount` не заменяет affinity; Docker argv не заменяет чтение ограничений. Самовольно переключать host cgroup или WSL запрещено.

Полный план: заранее объявленные **не менее шести чётных сбалансированных пар**, seed, порядок и фиксированная остановка без продления до «хорошего» результата. Минимальный текущий план равен шести парам. Сохранять все попытки, в том числе сбои/тайм-ауты, в новых каталогах. Число успешных операций за фиксированное время не обязано совпадать; совпадает определение нагрузки. Проверять preload, exit/deadline, ответы, реальные hit/miss, доли операций, байты и размер резидентного набора; P06 намеренно создаёт давление, не гарантирует одинаковую резидентную кардинальность.

Текущий [contracts.py](../tests/platform/perf/contracts.py), строки 6–26, задаёт пороги и окно: минимум 6 выборок, span ≥ 3 с, gap ≤ 1,5 с, относительный drift ≤ 0,05, range ≤ 0,15, trim по 1 с, ratio tolerance 0,03, measurement 12 с. В [run.py](../tests/platform/perf/run.py), строки 193–198, подготовительный warmup 5 с выполняется другими соединениями и не объявлен достаточным прогревом JVM. Сначала проверить сходимость штатным валидатором; при её отсутствии `INCONCLUSIVE`. Если нужен более долгий прогрев/новое окно, отдельно заранее согласовать методику и новый harness identity, затем повторить обе стороны, а не выбрать удобный фрагмент задним числом.

Точный биномиальный интервал медианы шести независимых непрерывных стационарных отношений имеет покрытие min/max 96,875 %; независимость не следует из числа запусков. Три старые пары исследовательские, их min/max покрывает медиану лишь на 75 % при тех же предпосылках. Текущий `classify` сначала отвергает невалидные данные, затем даёт FAIL при нарушении медианного порога, PASS только при достаточном интервале внутри порога; если медиана проходит, но интервал пересекает порог, результат `INCONCLUSIVE`. Не менять это правило ради кандидата.

Масштабирование клиента P08 не объясняет автоматически P03.

### JFR до изменений

На отдельном разрешённом PID сначала проверить `jcmd <PID> help JFR.start` и `jfr metadata` выбранного JDK; настройки профиля проверить по фактическому файлу recording settings. Предлагаемый шаблон после разрешения: `jcmd <PID> JFR.start name=opt-baseline settings=profile duration=30s maxsize=64m filename=<new-diagnostic-dir>/baseline.jfr`. PID и каталог не готовые значения, подставлять только проверенный принадлежащий эксперименту процесс. `jfr summary <recording.jfr>` проверяет фактическое наличие событий после записи.

Полезные имена для **проверки доступности/включения**, а не обещание присутствия: `jdk.ExecutionSample`, `jdk.NativeMethodSample`, `jdk.ThreadCPULoad`, `jdk.CPULoad`; `jdk.JavaMonitorEnter`, `jdk.JavaMonitorWait`, `jdk.ThreadPark`; `jdk.ObjectAllocationSample` (оценка с весами), при отдельном разрешении более подробные `jdk.ObjectAllocationInNewTLAB` и `jdk.ObjectAllocationOutsideTLAB`; `jdk.GarbageCollection`, `jdk.GCPhasePause`, `jdk.GCHeapSummary`; `jdk.SocketRead`, `jdk.SocketWrite`. Сохранять thresholds, stack traces и потерянные события. События allocation не равны полному счётчику выделений, а отсутствие `JavaMonitorEnter` не доказывает бесплатность uncontended monitor.

Для `ReentrantLock` сегментов смотреть `ThreadPark` и стеки; для `synchronized` записи/аллокатора смотреть monitor contention. CPU в синхронном копировании на потоке-владельце цикла событий может задержать других клиентов без park/contended monitor. `TURN_BYTES` ограничивает транспортные шаги, но не прерывает один вызов движка, который синхронно копирует всё допущенное тело. Нельзя считать такую задержку сетевым ожиданием или лечить её автоматически virtual threads.

NIO socket events зависят от JDK, пути и порога; ими нельзя гарантированно пересчитать все короткие `SocketChannel.write`. Если данных мало, запросить отдельный короткий счётчик/системную сводку вызовов на изолированном стенде, с лимитом объёма и оценкой overhead; не добавлять её скрытно в приёмочный прогон. Стеки не доказывают число syscalls, Java wrappers могут устраняться JIT.

## Технический список работ

В каждом OPT действуют общие правила выше, полный gate ниже и индивидуальный контроль. Указанные трудоёмкость/риск относительные: S = локальная правка, M = несколько контрактов/путей отказа, L = изменение владения с отдельным ADR. Это не календарные обещания.

### OPT-00. Валидный baseline и профиль

**Приоритет P0; трудоёмкость M; риск измерений высокий.** Точки: `SCENARIOS`, `WINDOW_CONFIG`, `classify` в [contracts.py](../tests/platform/perf/contracts.py):6–90; `Collector` и план повторов в [run.py](../tests/platform/perf/run.py):193–198,353–424. Факт: текущий smoke не соответствует требованиям v2; гипотезы о причинах ещё не проверены.

Действие: квалифицировать исходный кандидат на доступном cgroup-v2 стенде, затем отдельные короткие JFR по таблице. Альтернатива при отсутствии стенда: продолжить только статический анализ, сохранить `INCONCLUSIVE`, не имитировать поля cgroup. Контроль: A/A, негативные fixtures harness с испорченными ответами, пропущенной парой/хешем/exit/preload. Память диагностики отдельно от продуктовых бюджетов; только владелец процесса завершает его по deadline. Ожидаемый результат: воспроизводимая исходная линия, не ускорение. Зависимость всех OPT: закрытый OPT-00; остановка при несходимости/смене identity/ошибке оракула, откат состоит в отказе от численного вывода, не в удалении raw.

### OPT-01. Искать класс без обхода статистики

**P1, S, низкий/средний риск.** [DefaultCacheEngine](../src/main/java/ru/octomem/engine/DefaultCacheEngine.java):`admit` 296–318, `classFor` 749–754 вызывает `allocator.classStats(i).chunkSize()` по классам. [FfmSlabAllocator](../src/main/java/ru/octomem/storage/FfmSlabAllocator.java):`classStats` 224–240 под общим lock обходит страницы и создаёт `ClassStats`; `sizes` неизменен после конструктора, `allocate` 134–136 уже использует binary search. Факт: для выбора размера вычисляются ненужные динамические поля. Гипотеза: это заметная доля SET CPU/allocations при росте страниц.

Предпочтительный будущий вариант: один раз получить ограниченный массив геометрии при создании движка и делать lower-bound lookup без повторных статистических снимков. Альтернатива: узкий стандартный метод геометрии/поиска в `MemoryAllocator`, без зависимости engine от конкретного FFM backend. Выбор интерфейса у координатора. Не дублировать формулу роста 1,25 независимо от аллокатора: это риск расхождения терминального класса и округления.

Массив размером O(число классов) принадлежит движку, учитывается в фиксированных heap-метаданных до start; не per-command, не новая lease и не обход лимита native admission. Сохранить class ID, alignment, maxBlockSize и значение `-1` за пределом; lookup не обещает, что allocation пройдёт. A/B по первой строке таблицы, дополнительный контроль с пустыми/многими страницами одинаковых классов. Проверить независимо все границы классов ±1 и финальный максимум; будущий отдельный тест lookup ещё нужно написать. Уже есть `FfmSlabAllocatorTest`, `EngineAcceptanceTest`, `EngineRegressionTest`, `StatsDistinguishingAcceptanceTest.a11MultiplePagesPerClassZeroAndNonZeroFlagsAndPageTrim`.

Ожидается меньше admission CPU и временных статистических объектов, не изменение M3 заранее. Зависимость: OPT-00; откат: вернуть прежний lookup одним кандидатом. Стоп: любой неверный class/OOM/stats, измеримое ухудшение p99 или отсутствие выигрыша сверх A/A шума. Не включать сюда оптимизацию eviction.

### OPT-02. Укрупнить ограниченное копирование и вывод

**P1 после OPT-01; M, высокий риск lifetime/fairness.** [NioTransport](../src/main/java/ru/octomem/transport/NioTransport.java):`LANE_BYTES` 61, `acceptConnections` 237, `Connection.pump` 505–575, `accept` 596–598; [TextProtocolEncoder](../src/main/java/ru/octomem/protocol/TextProtocolEncoder.java):`Writer` 56–57, `writeMore` 145,237–251; [StoredItem](../src/main/java/ru/octomem/storage/StoredItem.java):`Reservation.finish` 75–92, `View.readValue` 605–624; [FfmSlabAllocator](../src/main/java/ru/octomem/storage/FfmSlabAllocator.java):`Handle.read/write` 400–431.

Факт: 64 KiB требует не менее 256 payload-read частей при scratch 256 и порядка 128 полных transmit-lane ёмкостей по 512, плюс framing. Для 1 048 000 байт нижняя оценка 4094 частей и 2047 ёмкостей. Framing/allowance/partial write могут увеличить работу; эти числа **не измеренные syscalls**. Каждая native-копия берёт общий lock и создаёт slice/buffer views; долю CPU/элиминацию объектов покажет профиль.

Первый вариант: согласованный ограниченный outbound burst по ADR-016, например 8 KiB на активную выдачу при успешном резервировании, с 512-байтной собственной lane как обязательным fallback. Альтернатива: отдельно увеличить только scratch синхронного копирования движка с 256 до 4 KiB на поток-владелец либо одну операцию при заранее учтённой плате. Это **разные A/B-кандидаты**: увеличение одного scratch при прежнем sink 512 не даёт автоматически крупного socket write. Для `capture(..., touch=true)` сейчас scratch всего 32 байта (DefaultCacheEngine:605); проверить multi-gat отдельно, не экстраполировать SET.

Порядок работы с burst: checked reserve глобального и локального бюджета до allocation, отсутствие резерва ведёт к собственной lane без ожидания другого клиента. Буфер с неотправленными байтами принадлежит конкретному connection до drain/cancel; его нельзя вернуть общему владельцу на yield. Общий scratch цикла разрешён лишь на синхронном участке, без сохранения ссылок после возврата, reentry либо передачи другому потоку. Byte/step quota остаются конечными; размер единичной копии не должен поглотить весь turn без проверки fairness.

Не выносить `MemorySegment` наружу и не снимать allocator lock как побочный эффект. Текущий порядок при чтении: table segment (при поиске), затем record monitor, затем allocator monitor; сетевого I/O внутри них нет. Lease удерживает immutable версию до последнего чтения; после копирования в собственный транспортный буфер snapshot можно закрыть, но не пока очередь ссылается на native-память. Arena закрывается только после освобождения последнего блока страницы, не при завершении одного writer. Любая новая схема read-pin/lock требует отдельного ADR и доказанного happens-before.

A/B: P05 и малый контроль из таблицы, плюс активный маленький клиент рядом с медленным большим читателем. Ожидается меньше копий/monitor acquisitions/write на байт, ниже CPU/байт и p99, выше bytes/s; возможен рост RSS. Регрессии: `TextProtocolEncoderTest`, `TransportFaultAcceptanceTest.forcedZeroAndPartialWritesResumeWithoutReencodingAndIoFailureClosesWriter`, `TextConnectionSocketTest.throwsDisconnectAndShutdownCloseDelegatesAndBudgetsOnce`, `StoredItemConcurrencyTest`, `FfmSlabAllocatorConcurrencyTest`, `NioTransportTenThousandIT`. Независимо добавить исчерпание burst и fairness нового пути: существующие тесты не доказывают ещё не написанный механизм. Стоп/откат: регрессия малого p99, lifetime/budget leak, поздний OOM после VALUE, рост RSS без допустимого бюджета; отключить новый путь и вернуться к старому кандидату. Зависимости: OPT-00, учёт из раздела бюджета, согласованное владение.

### OPT-03. Объединить короткие ответы без очереди команд

**P2, M, высокий риск порядка и задержки.** Факт: `NioTransport.Connection.pump` 509–527 сбрасывает transmit перед дальнейшим writer/декодированием; [TextConnectionHandler](../src/main/java/ru/octomem/transport/TextConnectionHandler.java):`handle/encode` 42–76 допускает один ответ, `OwnedWriter.close` 143–150 освобождает предыдущую команду. Pipeline 100 не означает 100 ответов в одном write. Гипотеза: маленькие STORED платят непропорционально много за flush и переходы состояния.

Вариант: завершать и закрывать writer после копирования короткого ответа в уже зарезервированный transmit, затем заполнять остаток следующими готовыми ответами строго по порядку. Не хранить список ответов/borrowed commands. Альтернатива: фиксированный малый coalescing-буфер из OPT-02; сначала проверить batching внутри существующих 512 байт. Flush обязателен перед ожиданием чтения, при полном буфере, окончании turn, ошибке/закрытии согласно wire-контракту; нельзя ждать следующую команду, удерживая её необходимый ответ. Максимум команд и байт за turn считать отдельно от числа внутренних шагов; значения сначала предложить и измерить, не менять текущие defaults.

Перед следующим decode закрыть предыдущие response/command/body/token ровно один раз; transport line-slot учитывать до согласованной границы. `quit`, fatal error, `noreply`, частичная запись и shutdown не должны потерять уже скопированные ответы или начать новый decode после закрытия. Native lease не хранится за копией. A/B P03 против P02, отдельный latency-sensitive клиент и disconnect на границах 1/99/100; ожидается меньше write/SET и больше throughput, но p99 одиночного запроса может вырасти. Есть `TextConnectionSocketTest.pipelinedVersionsReleasePreviousBorrowBeforeNextDispatch`, `completeZeroNullAndNoreplyStoresKeepPipelineAndBorrowAlive`, `fatalMalformedTerminatorFlushesSafeErrorAndNeverDispatchesTail`, `TextProtocolEndToEndTest`, `TransportFaultAcceptanceTest`. Новый независимый oracle должен проверить точные 100 ответов с ошибкой внутри, без сортировки результатов. Зависимость: OPT-00, бюджет/профиль OPT-02; стоп при задержанном ответе pipeline 1, starvation, изменении EOF/порядка; откат только batching, не тестовых ожиданий.

### OPT-04. Убрать подтверждённые временные копии

**P2, M; streaming ingress отдельно L.** [TextProtocolDecoder](../src/main/java/ru/octomem/protocol/TextProtocolDecoder.java):`append` 160–165 выделяет/растит line, `clearResources/reset` 228–245 обнуляет ссылку; `parseLine` 321–330 копирует ключ и выделяет допущенный body. `DefaultCacheEngine.Incoming` 289 клонирует ключ; [CacheCommandDispatcher](../src/main/java/ru/octomem/protocol/CacheCommandDispatcher.java):`execute` 132–139 ещё материализует mutation-key через `SingleKey`. `preparedStore` 339 и encoder `Writer` 56–57 выделяют scratch; `Reservation.finish` копирует body через scratch в native. Факты размещения в коде не гарантируют surviving allocations после JIT.

После allocation-профиля первым отдельным кандидатом сделать повторное использование небольшого scratch владельцем синхронного вызова либо исключить одну доказанно избыточную key-copy через явный borrowed slice до command release. Альтернатива: оставить копию ≤ 250 байт как дешёвую границу владения, если профиль её не выделяет. Line reuse требует платы за удержанный idle-массив, ограничения retained capacity и очистки; нельзя обнулить logical charge, оставив большое backing на 10 000 idle connections. Не вводить глобальный pool без верхней границы и не помещать payload целиком во второй новый массив.

Полное устранение body byte[] через streaming в неопубликованный native reservation не первая правка: parser сейчас проверяет CRLF до выполнения команды, держит атомарный резерв, умеет drain отказа и cancel. Новый путь требует ADR, сохранения старого значения при malformed/EOF, резервирования до read, единственного владельца и точного rollback. Сначала безопаснее укрупнение синхронного copy из OPT-02, а не смена admission-контракта. Async/thread-offload не предлагается: он меняет ownership, reentry и срок жизни borrowed buffers.

A/B по таблице, контроль idle P08 после завершения нагрузки; ожидается снижение allocation bytes/op и GC CPU, но не гарантированное снижение RSS. Регрессии: `TextProtocolDecoderTest`, `ParsedCommandTest`, `TextConnectionHandlerTest`, `ConnectionResourcesAcceptanceTest`, `TextConnectionSocketTest.realGlobalBodyDenialDrainsNoreplyAndDoesNotReleaseOtherOwner`, `StatsDistinguishingAcceptanceTest.a14ReservationFinishAndReleaseFailClosed`, `EngineRegressionTest.genuineReadFailureDuringSingleReplacementPreservesOldPinAndValue`. Независимо добавить overwrite borrowed backing после release для нового пути. Зависимости: OPT-00/02/03 измерены отдельно; стоп при росте idle retention, double release, stale key/body, новых больших полных копиях; откат к прежнему владельцу и копиям.

### OPT-05. Сократить бесполезную работу admission/eviction

**P2 по профилю, M/L, высокий риск семантики.** `DefaultCacheEngine.preflight` 716–746: четыре фазы, обход сегментов/классов, trim; `admit` 303–318 до 1024 повторных попыток после отказов. [SegmentedItemTable](../src/main/java/ru/octomem/storage/SegmentedItemTable.java):`Transaction.removeLeastRecent` 573–588 просматривает до 1024 записей в точном class-LRU порядке, исключая pinned/target через predicate. `FfmSlabAllocator.allocate` 137–151 ищет свободный блок по страницам, `releaseEmptyPages` 316–339 обходит классы. Работа ограничена, но произведение границ может быть дорогим; это не неограниченный цикл.

После OPT-01 отдельно оценить ограниченный индекс непустых классов для сокращения внешнего перебора или список страниц с доступными slots внутри существующего allocator lock. Пустой head уже проверяется за O(1) в `removeLeastRecent`: не добавлять второй такой же check под видом ускорения. Альтернатива: метаданные числа пустых страниц для дешёвого решения о необходимости trim. Только один механизм за кандидат. Нельзя ради скорости уменьшать глубину 1024, менять LRU на случайную жертву, пропускать защищённые targets или вводить cached availability без актуализации после allocate/free/trim/close. Новый указатель/счётчик требует heap charge, атомарного обновления под владельцем, rollback при ошибке публикации и проверки после последнего pin release.

A/B P06 после установившегося давления, контроль тот же SET ниже ёмкости и `noeviction`; отдельно same-class/cross-class pressure. При JFR искать `classStats`, `removeLeastRecent`, `keyEquals`, `trim`, блокировки; измерять, сколько реальных жертв потребовалось на успешный SET, а не снижать resident set ради скорости. Ожидается меньше scans/retries/CPU на принятую запись, лучше p99 без лишнего eviction. Тесты: `ClassQueueAcceptanceTest.leastRecentRemovalHonorsBoundedEligibilityAndClass`, `EngineRegressionTest.repeatedAllocationDenialStopsAfterBoundedRetriesAndProtectsTarget`, `oneChunkPressureEvictsExactlyOneAcrossEightSegments`, `trueClassLruFindsSixtyFifthRecordBeyondFormerSample`, `emptyPageTrimAdmitsDifferentClassWithoutLiveEviction`, `T013RetryAcceptanceTest`. Новый индекс страниц дополнительно проверять независимым полным обходом состояния в тесте. Зависимость: OPT-00/01; стоп при изменении жертвы, лишнем OOM/eviction, live-page close или потере bounded retry; откат вспомогательного индекса целиком, не ослабление тестов.

**Уточнение контроля `noeviction`:** в предыдущем абзаце это только дополнительный внутренний engine-fixture, не настройка публичного P06. [ConfigLoader](../src/main/java/ru/octomem/config/ConfigLoader.java):190–195 принимает только `lru`; внутренний `DefaultCacheEngine.Settings`:59–67 допускает `noeviction`. Публичное сквозное сравнение обязательно остаётся на `lru`. Отдельный ограниченный микропрогон движка может использовать внутренний `Settings(..., "noeviction", ...)` только со своим согласованным драйвером и identity, не заменяет обязательный P06 и не разрешает расширять публичный конфигурационный контракт.

### OPT-06. Метаданные, память и только затем JVM

**P3, M для локального layout, L для lifetime; риск высокий.** `StoredItem` 26–53,178–189 хранит объект lock, handle, primitive metadata, intrusive links и `ByteBuffer.allocate(8)` для `keyEquals` 469–500. `SegmentedItemTable` 844–869 хранит segment locks, buckets и Entry. `FfmSlabAllocator` 157–170,253–283 имеет free-slot int[] на страницу; `ServiceBudget.CHARGE=512` (StoredItem:129–156) означает консервативную логическую плату версии, **не RSS/запись**. В коде уже есть classNumbers/classBytes: не предлагать их как отсутствующие.

После профиля и раздельных quiescent/active окон выбрать один компонент: например заменить per-record keyScratch на стандартное ограниченное сравнение native-байтов внутри владельца allocator либо на доказанно thread-confined scratch. Альтернатива: сохранить layout и исследовать вклад bucket/page metadata при одинаковых native budgets. Нельзя хранить вторую постоянную heap-копию значения, использовать Unsafe/reflective Cleaner/внутренние JVM API, добавлять runtime dependencies или закрывать arena раньше последнего читателя. Замена lock/handle/lease модели не локальная «экономия объектов» и требует ADR; существующий порядок segment → record → allocator не инвертировать.

Для 1 MiB страницы класса 64 free-slot данные составляют `4 × floor(1048576 / 64) = 65536` байт, модель страницы `65536 + 24 + 256 = 65816` heap-байт. Это конкретная модель metadata, не резидентный размер всей страницы или процесса. Любое уменьшение conservative charge сначала подтверждать layout в поддержанных pointer modes, а не подгонять к M3. Retired pinned версии и неопубликованные reservations остаются оплачены; free блока, trim страницы и снижение RSS различны.

NMT только в отдельном диагностическом процессе, предложенный стартовый параметр `-XX:NativeMemoryTracking=summary`; после проверки `jcmd <PID> help VM.native_memory` использовать `VM.native_memory baseline`, затем `VM.native_memory summary.diff`. NMT reserved/committed не RSS; полноту учёта FFM проверить, не предполагать. Отдельно предложены `-Xlog:gc*` с ограниченным файлом/ротацией и GC-события JFR. Не выполнять `GC.run` внутри timed workload, не подменять M3 памятью после forced GC; heap histogram/attach также меняют процесс и нуждаются в своём диагностическом прогоне.

Если данные указывают на GC/commit, сравнить лишь одну GC/heap-настройку за раз на той же OpenJDK 25, при одинаковом CPU/native/общем memory budget, с JDK availability check и полным flag dump. Тестовый `UseSerialGC` в команде Java gate не default продукта. Ни конкретный GC, ни Xms/Xmx не меняются в продукте до ADR-решения; 21 не автоматический fallback. A/B M3 и активная P04/P05/P08, контроль прогретый пустой процесс; ожидается уменьшение конкретного retained компонента/общего RSS, возможен обмен на CPU/p99. Не выводить асимптоту по трём маленьким наборам.

Тесты: `PageMetadataAccountingTest`, `StoredItemTest`, `StoredItemConcurrencyTest`, `FfmSlabAllocatorFailureTest`, `FfmSlabAllocatorConcurrencyTest`, `EngineRegressionTest.serviceMetadataChargesRetiredOwnerUntilLastPinAndRollsBackFailures`, `OwnershipClientContractTest`, `NioTransportTenThousandIT`. Новому сравнению ключей нужны независимые collision/длины 1–250/offset oracle, новому layout отдельный bounded probe. Зависимость: OPT-00 и повторное измерение после allocation-правок; стоп при недоучёте charge, memory corruption, ложном keyEquals, GC/p99 regression или RSS без устойчивого окна; откат layout/flags к зафиксированному A. Достижимость M3 остаётся открытым измерительным вопросом.

### OPT-07. Дешёвый учёт только по свидетельствам

**Условный P3, S/M, средний/высокий риск наблюдаемой семантики.** Факт: `DefaultCacheEngine.gauges` 212–217 синхронизируется на `items` и публикует два gauge; вызывается в finally, в том числе `read` 265 и `capture` 659. [AtomicStatsRegistry](../src/main/java/ru/octomem/stats/AtomicStatsRegistry.java):`add` 120–126 выполняет saturating CAS, `incrementClass` 188–195 обновляет class/global в одной epoch. При этом `snapshot` 144–156 создаётся при запросе статистики; нет основания объявлять его выделение на каждый GET.

Если профиль показывает заметную цену неизменных gauge-публикаций, кандидат: не публиковать их там, где гарантированно не менялось состояние. GET может лениво удалить expired запись, а capture тоже меняет счётчики/состояние, поэтому безусловное удаление finally неверно. Альтернатива: согласованная публикация при изменении с доказанной защитой от запоздалого overwriting; thread-local batching counters только отдельное решение, так как reset epoch, точные дельты и saturation наблюдаемы. Не отключать stats, не заменять atomics приблизительными значениями молча.

Дополнительный флаг/плата принадлежит операции либо фиксированному registry, не создаёт unbounded очередь и не удерживает lease. A/B из таблицы с одинаковой частотой stats-запросов; отсутствие внешнего опроса контроль, не удаление учёта из продукта. Ожидается меньше contention/CPU, не гарантированный gain. Регрессии: `StatsConcurrencyTest`, `StatsRegistryTest`, `StatsEngineAcceptanceTest`, `StatsWireAcceptanceTest`, `StatsDistinguishingAcceptanceTest.a18ConcurrentResourceUsageObserverAndResetStaySafe`, истечение при GET, reset одновременно с операциями, насыщение и дельты ошибок. Зависимость: OPT-00 и подтверждённый стек; стоп при stale gauges/потере дельт/reset, отсутствии эффекта; откат publication policy, не ослабление oracle.

### P07-B. Кандидаты: ровно один механизм на изменение

Каждый кандидат — отдельный A/B и отдельный SHA-256. Первый кандидат выбирается только после закрытия P07-A ограниченным профилем; до этого ни один не реализуется.

- **P07-C1 (первый кандидат при подтверждении).** Один механизм: отдавать короткий ответ `VERSION` connect/version/close через уже имеющиеся ограниченные ресурсы соединения (собственная transmit lane и bounded writer владельца) вместо отдельного короткого объекта/копии на команду. Проводные байты, порядок и бюджет не меняются. Механизм совпадает с идеей OPT-03, но сужен до одной команды на соединение; это отдельное изменение, а не перенос OPT-03.
- **P07-C2.** Один механизм: переиспользовать два 512-байтных lane (сейчас `ByteBuffer.allocate(LANE_BYTES)` в `acceptConnections`) из ограниченного списка свободных на том же event-loop с обязательным fallback на свежую аллокацию. Wire/budget/ownership не меняются; учитывать удержанную idle-ёмкость.
- **P07-C3.** Один механизм: переиспользовать граф `ConnectionResources` + handler/decoder/encoder, создаваемый `factory.create` на соединение. Меняет срок жизни объектов соединения — отдельный ADR, отдельное доказательство happens-before, не локальная экономия.
- **P07-C4.** Один механизм: сократить syscall/selector/публикации gauges на жизненный цикл (`key.cancel`, закрытие сокета, публикации под `admission`) без изменения семантики и отчётности.

C1–C4 не смешивать в одном кандидате. C2–C3 меняют владение/срок жизни и требуют решения владельца архитектуры.

### P07-C. Обязательные отрицательные контроли

- A/A на неизменённом A: полезный эффект принимается только если он превышает разброс A/A.
- «Нейтральный» B (перестановка, не меняющая работу) не должен двигать CPU/цикл сверх A/A; иначе измеритель негоден.
- Соединение, оборванное до `VERSION` (RST/полузакрытие), не оставляет арендованных ресурсов/утечек.
- `quit`, ошибка, idle-timeout, превышение `connections.max` сохраняют поведение и точные байты `VERSION`/EOF.
- Переиспользуемый ресурс не несёт байты предыдущего соединения (отдельный byte-oracle).
- Нет незавершённых воркеров/потоков; внешний deadline обязателен; ошибка/незавершённый воркер делает команду ненулевой.

### P07-D. План измерений

- Сценарий строго как в `contracts.py`: P07 = (0, 0, 1, "0:0", 1, 256), `kind=cycles`; один запуск, затем 100 циклов connect/version/close.
- Пары: не менее шести чётных сбалансированных чередующихся пар, отдельная warmup-строка на пару, фиксированная остановка без продления до «хорошего» результата. Все попытки сохраняются.
- Окна: M1 — отношение сумм 100 циклов; M2 — отношение 99-й упорядоченной задержки цикла; M3 для P07 остаётся INCONCLUSIVE, пока для него не объявлено отдельное стационарное RSS-окно в новом контракте.
- Холодную/стационарную характеристику вести только как отдельную заранее объявленную серию; задним числом фрагмент не выбирать.
- Идентичности: кандидат JAR со своим SHA-256 (текущий `950a8edb702e51c9979320c117257426f1109076845e80f30774ef0855ff682b`), JDK 25 Temurin `25.0.4.1+1` `7380ce48…`, эталон memcached `1.6.45` `3b3d4250…`, `generator.py` `473eaf39…`, pinned harness `run.py 07b07ea6…` / `contracts.py 244be682…` / `gates.py 12437375…` / `finalize.py 9cc15c1a…`. memtier для P07 не применяется.
- Профиль: отдельный ограниченный JFR на форме P07 (например 30 с, 64 MiB) и A/A с профилем и без него; PID и каталог только проверенные, диагностическая память отдельно от продуктовых бюджетов.

### P07-E. Правило отката

Один кандидат — один механизм. При регрессии валидности, справедливости, владения или утечки, при росте p99 сверх A/A-шума либо при отсутствии снижения CPU/цикл сверх A/A-шума кандидат откатывается к A целиком; raw сохраняется, тесты и пороги не ослабляются.

### P07-F. Правило инвалидации

Любое изменение продукта даёт **новую идентичность JAR со своим SHA-256**. Затронутые обязательные наборы TEST-01…09 перезапускаются на новой сборке; сравнение с `950a8edb…` остаётся историческим. Существующий 72-часовой endurance PASS относится только к `950a8edb702e51c9979320c117257426f1109076845e80f30774ef0855ff682b` и **никогда не переносится** на изменённый кандидат. Старые raw, паспорта и отчёты не переписываются и не переименовываются под новый hash.

## Бюджет буферов

Примеры ниже арифметические, не новый default и не RSS-оценка. `MiB = 1024 × 1024`. Текущий `CONTROL_CHARGE=10816` включает lanes, bridge, writer и dispatcher; старую базовую строку `1088` в ADR нельзя принять за полную текущую плату.

| Пример для 10 000 соединений | Арифметика | Последствие |
|---|---|---|
| Две нынешние lane по 512 | `10000 × 2 × 512 = 10240000` байт, 9,765625 MiB payload | С двумя allowance по 32: 10 880 000 байт; ещё не весь control graph |
| Текущий aggregate control charge | `10000 × 10816 = 108160000` байт, 103,149414 MiB | Логический резерв держится и при idle; фактический heap/RSS измеряются отдельно |
| Ошибочное увеличение обеих lane до 64 KiB всем | `10000 × 2 × 65536 = 1310720000` байт, 1250 MiB только payload | Даже одна lane всем: 625 MiB; прежний charge перестаёт покрывать память |
| Предлагаемый общий 8 MiB burst, chunk payload 8 KiB, allowance массива 32 | `floor(8388608 / 8224) = 1020` одновременно допущенных chunk, остаток 128 | Только верхний расчёт массива: descriptors, queue и прочие wrappers уменьшают реальный предел |
| Предлагаемый синхронный scratch 4 KiB на 4 owner loops | `4 × 4096 = 16384` байт плюс wrappers | Допустим только без удержания между вызовами/потоками; не заменяет per-connection pending transmit |

Пул 8 MiB допустим лишь как пример внутри согласованного `min(memory.limit, 64 MiB)` outbound cap; при меньшем лимите уменьшается, собственная control lane остаётся рабочей. Реальный chunk charge должен покрыть всю новую graph; локальный `pendingWriteBytes` и `maxChunkBytes` действуют одновременно с глобальным лимитом. Checked long, резерв до allocation, учёт одновременных old/new при замене буфера, exactly-once release на drain/error/cancel/disconnect/shutdown обязательны. Не считать body/snapshot/native резерв свободным местом для нового scratch: это разные владельцы и разные сроки жизни.

## Проверка и порядок

Существующие команды из [tests/README](../tests/README.md), запускать **позже после отдельного разрешения**, из корня проекта; в этой задаче они не запускались:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run-checks.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run-checks.ps1 -FullJava -JavaHome C:\java\octomem.octocode.tech\.tools\jdk\jdk-25.0.4.1+1
```

Полный Java gate перезаписывает `target`, поэтому прежние доказательства сохранить заранее и сериализовать builds/socket-heavy tests. Будущий новый JAR получает собственный hash/pin через согласованный процесс, нельзя запускать изменённый артефакт под pin `637640…` или отключать проверку равенства. Для каждой OPT сначала точечные указанные классы в обычном Java gate, затем полный gate с неизменными coverage. Имена новых тестов/профильного subset runner здесь не выданы за существующие команды.

Карта существующих тестов: [engine](../src/test/java/ru/octomem/engine/), [storage](../src/test/java/ru/octomem/storage/), [transport](../src/test/java/ru/octomem/transport/), [protocol](../src/test/java/ru/octomem/protocol/), [stats](../src/test/java/ru/octomem/stats/), [statsacceptance](../src/test/java/ru/octomem/statsacceptance/), [contracts](../src/test/java/ru/octomem/contracts/). Имя класса из OPT соответствует файлу `<ClassName>.java` в этих каталогах; классы harness находятся в [tests/harness_tests](../tests/harness_tests/).

Текущий `tests/platform/perf/run.py` запускает **полную кампанию**, не один сценарий. Пример существующего интерфейса для отдельного разрешённого baseline на подготовленном стенде:

```bash
python3 -B tests/platform/perf/run.py --output-parent /new/evidence-parent --java /absolute/jdk25/bin/java --java-version 25.0.4.1 --reference /absolute/memcached --jar /absolute/current-candidate.jar --client /absolute/memtier_benchmark --repetitions 6 --approved-run
python3 -B tests/platform/perf/finalize.py --input /existing/attempt --output /new/analysis-directory
```

Пути примерные, `--approved-run` не создаёт разрешение само по себе. Для коротких A/B из таблицы нужен отдельно согласованный bounded driver/subset, которого этот документ не создаёт; не запускать full collector для «быстрой пробы». Оракул: независимый автор проверяет точные bytes/length/order/EOF, payload pattern и resource deltas до закрытия allocator; сравнение с эталоном дополняет, но не заменяет контракт, потому что оба сервера могут одинаково ошибиться. Будущие статистические счётчики копий/сканов также независимы от проверяемого результата: не считать саморепорт единственным доказательством.

Порядок реализации:

1. OPT-00: новый baseline, cgroup v2, устойчивые окна, минимум шесть пар, затем JFR и контроль overhead.
2. OPT-01: низкорисковый lookup; полный regression gate, один новый кандидат, повтор профиля.
3. OPT-02: один bulk-I/O/copy механизм, bounded budget, slow-reader/fairness/pin проверки.
4. OPT-03: batching коротких ответов, только если профиль P03 подтверждает цену flush.
5. OPT-04: одна allocation-правка, перепроверка active/idle retention. Не смешивать со streaming ingress ADR.
6. OPT-05 выполнять после lookup, когда pressure-профиль подтверждает оставшиеся обходы; OPT-07 только при подтверждённой цене учёта.
7. OPT-06: retained metadata и отдельные GC/NMT диагностические сравнения после стабилизации предыдущих кандидатов. Defaults до ADR не менять.
8. На выбранном едином кандидате повторить затронутые обязательные TEST-01…09 и согласовать полный релизный комплект; эта работа не проводит 72 часа и не квалифицирует вторую ОС.
