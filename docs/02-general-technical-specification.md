# octomem: общее техническое задание

Версия 0.1 от 14.09.2026. Проект требований до начала разработки.

## 1. Назначение и область

Настоящее ТЗ определяет требования к серверу `octomem` — самостоятельной реализации сервера кеширования, совместимого с текстовым протоколом Memcached.

Область 1.0: один процесс, память, сеть, текстовый протокол, ограничение памяти, срок жизни, вытеснение, статистика, командная строка и файл конфигурации, сборка и поставка.

Вне области 1.0: постоянное хранение, кластер, Redis-команды, бинарный протокол, мета-команды, аутентификация, графический интерфейс, шифрование канала. Основные понятия и границы — в [продуктовом брифе](01-product-brief.md).

Структура документа свободная. Формальное соответствие ГОСТ 19.201 или 34.602 не заявляется; при требовании договора оформляется отдельный проход по форме.

Термины совпадают с глоссарием в [01](01-product-brief.md#10-глоссарий). Дополнительно:

- **Клиент** — библиотека Memcached в приложении.

- **Известное отличие** — задокументированное расхождение с эталоном.

## 4. Контекст системы

```text
        +-------------------+        TCP (текстовый протокол)
        |  Приложение       |<---------------------------------+
        |  клиент Memcached |                                  |
        +-------------------+                                  v
                                                      +---------------+
        +-------------------+    stats, мониторинг     |   octomem     |
        |  Эксплуатация     |<-------------------------|   (процесс)   |
        +-------------------+                         +---------------+
```

Внешние интерфейсы octomem: сетевой порт по протоколу Memcached, файл конфигурации, аргументы командной строки, стандартный вывод и журнал. Внешних баз данных, брокеров и облачных сервисов нет.

## 5. Сценарии использования

- **UC-01.** Разработчик направляет кеш-запросы приложения на octomem, не меняя код.
- **UC-02.** Эксплуатация задаёт предел памяти и порт, запускает сервер, наблюдает метрики.
- **UC-03.** Приложение хранит, читает, изменяет и удаляет записи, использует `cas` и счётчики.
- **UC-04.** Эксплуатация очищает кеш командой `flush_all` без перезапуска.
- **UC-05.** При исчерпании памяти сервер вытесняет давно неиспользуемые записи и продолжает работу.

Native memory.limit и отдельные heap-бюджеты ADR-016 не являются пределом RSS и не меняют четырнадцать defaults.

### 6.5. Эксплуатация

Уточнение F1/F2/F3 к ADR-016: `memory.limit` остаётся native cache budget. Heap body cap `max(item.maxSize+32,min(memory.limit,64 MiB))` допускает любой настроенный valid item в одиночку; целый payload+32 резервируется до чтения, отказ приводит к framed drain/OOM, не ожиданию частичного тела. Control pool `544*2*connections.max` резервирует каждой принятой сессии receive/discard512 и transmit512 независимо от optional burst `min(memory.limit,64 MiB)`; нормальные ответы/ошибки/CRLF2 сохраняют прогресс при tiny memory.limit. Snapshot cap прежний `min(floor(memory.limit/16),16 MiB)`, плата `512+512*N` обоснована шестью массивами ADR-016 F3 и проверяемыми layout assumptions. Это проектные ограничения, не новые настройки/defaults и не RSS-гарантия; приёмка ещё требуется.

## 7. Нефункциональные требования

### 7.1. Производительность и ёмкость

Line/descriptor ADR-016 M1/M2: charge `2L * L + 256` для int L=maxLine, perconn `satMul(maxInflight,charge)`, global `satMul(connections.max,perconn)`. Только производные LIMIT насыщаются до Long.MAX_VALUE без config rejection/урезания публичных пределов; actual reserve проверяет `charge <= limit-used`, реальные платы/счётчики не насыщаются. Slot ленивый до чтения, full pipeline отключает OP_READ без body reserve ради slot, control продолжает ответы. Engine.KeySequence заимствует immutable raw line до command release, считает N одним scan и передаёт backing/offset/length последовательным visitor без per-key объектов/массивов/List. Геометрический backing≤L имеет пик old+new≤2L и overhead256 по ADR-016, без shrink-copy. Snapshot reserve перед allocation массивов, оба резерва учтены до handoff. Это пятый heap-пул, не новый ключ, не eager ceiling allocation и не RSS-гарантия.

## 9. Поставка

Обязательная матрица ограничений реестра: [REG-01…REG-14](ref-registry-research.md). До выбора хранения/компиляции и передачи исходников внешним сервисам проверить REG-01/03/07/08/09. Права, финансовые условия и юридическая применимость не подтверждаются тестами сервера. Подача и публикация требуют отдельного разрешения владельца.

Состав поставки 1.0:

- исполняемые файлы сервера и скрипты запуска;
- файл конфигурации по умолчанию;
- модуль примеров и утилита проверки конфигурации;
- документация: установка, настройка, эксплуатация, справочник протокола, известные отличия;
- лицензия и перечень сторонних компонентов;
- `SBOM` в открытом формате;
- контрольные суммы артефактов;
- комплект доказательств приёмки: отчёты Т-01…Т-09.

Поставка выполняется архивом и, при необходимости, пакетом для целевой ОС. Онлайн-активация и обязательные внешние сервисы отсутствуют.

## 10. Требования к документации

- Инструкция по установке и запуску, выполненная на чистом стенде.
- Описание конфигурации с указанием всех ключей и значений по умолчанию.

- Описание сборки и воспроизводимости.
- Лицензия и `NOTICE` сторонних компонентов.

## 11. Приёмка (высокоуровневая)

Выпуск 1.0 принимается при одновременном выполнении:

1. Пройдены все обязательные тесты Т-01…Т-09 без пропусков.
2. Достигнуты относительные показатели M1–M7 из [01](01-product-brief.md#6-показатели-успеха).
3. Все известные отличия от эталона задокументированы и приняты.
4. Нет открытых критических и высоких дефектов.
5. Поставка воспроизводится на чистом стенде.
6. Реестровые доказательства собраны по [09](09-acceptance-and-registry-readiness.md).

Трассировка «требование → ЧТЗ → тест → критерий» приведена в [09](09-acceptance-and-registry-readiness.md).
