# octomem: комплект проектной документации

Версия 0.1 от 14.09.2026. Статус: проектная документация до начала разработки.

`octomem` — самостоятельная реализация сервера кеширования, совместимого с протоколом Memcached на уровне сети. Продукт заменяет Memcached в приложении без переписывания логики: меняется адрес сервера, а клиентская библиотека остаётся прежней.

Здесь нет кода, сборок, результатов испытаний или поданной заявки в реестр. Это задание на разработку: что сделать, как проверить и по каким критериям принимать.

Актуальные замечания к комплекту: [ревью от 14.09.2026](review-2026-09-14.md). Оно содержит блокеры фиксации контрактов и не является отчётом об испытаниях продукта.

## 1. Назначение комплекта

Актуальная проверка совместимости: [отчёт 25.10.2026](compatibility-recheck-2026-10-25.md). Коррекция classic text внесена в docs/04, docs/05 и docs/06; [ADR-019](adr/ADR-019-wire-cas-and-set-failure.md) принят как дизайн после независимого ревью, реализация [T-018](../tasks/T-018-classic-compatibility-corrections.md) проходит полную проверку. Это не новая приёмка продукта и не снятие старых релизных блокеров.

Комплект рассчитан на автоматизированную и смешанную разработку. Его задача — быть настолько однозначным, чтобы агенты-исполнители могли делать законченный продукт по частям, а независимый проверяющий — принимать каждую часть отдельно.

Комплект отвечает на вопросы:

- что за продукт и для кого;
- какие функции обязательны, какие отложены и что запрещено;
- как устроена система и какие интерфейсы фиксированы;
- каким командам протокола и какому поведению обязан соответствовать сервер;
- какие тесты доказывают соответствие;
- как разбить работу на задачи для агентов;
- как принять результат и подготовить продукт к реестру.

## 4. Соглашения

- **Должен** — обязательное требование выпуска 1.0. **Следует** — желательное. **Может** — допустимое.
- **P1** — входит в выпуск 1.0. **P2** — следующая очередь, без обещания срока. **P3** — вне области.
- Идентификаторы требований: `FR-*` функциональные, `NFR-*` нефункциональные, `ЧТЗ-*` частные задания, `Т-*` наборы тестов. Текущие задачи реализации: `T-*`, релизных проверок: `TEST-*`; `ЗАД-*` только исторические идентификаторы.
- Все спорные случаи поведения протокола решает спецификация 04, затем поведение эталонного Memcached, затем решение архитектора.
- Формулировки о спросе и рынке не входят в этот комплект: он описывает только проектирование и приёмку.

## 5. Статус решений

| Решение | Значение | Как изменить |
|---|---|---|
| Язык реализации | Java | Через ADR в 03 |
| Транспорт | Собственный цикл на `java.nio` | Через ADR-004 в 03 |
| Хранилище | Собственная память, без диска | Через изменение 01 и 02 |
| Кластер | Отсутствует в 1.0 | P2 |
| Протокол 1.0 | Текстовый Memcached без мета-команд | Мета-команды — P2, бинарный протокол — P3 |
| Аутентификация 1.0 | Нет встроенной; совместимость только с unauthenticated-профилем Memcached по умолчанию | SASL и текстовая `-Y` не поддерживаются; обязательную защиту при миграции не отключать |
| Лицензия | Apache-2.0 (предварительно) | Решение правообладателя |

Изменение любого решения оформляется в документе-владельце и отражается в разделах «Изменения». Скрытые изменения запрещены.

## 6. Как поддерживать комплект

1. Любое изменение контракта протокола начинается в 04, затем отражается в 05, 06 и только потом в коде.
2. Любое архитектурное изменение оформляется новым ADR в 03, старый не удаляется.
3. Новая задача добавляется отдельной карточкой в соответствующий исполняемый каталог и его `00-index.md`, с идентификатором, зависимостями и критериями. Историческую таблицу `ЗАД-*` не пополнять.
4. Комплект версионируется вместе с продуктом. Версия комплекта и версия продукта связаны в 07.
